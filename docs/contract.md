# Контракт блока и формат пайплайна

Контракт — это договор, по которому стыкуются все части платформы: движок, блоки, адаптеры, редактор. Кто соблюдает договор, тот встаёт в платформу без переделок. Здесь он описан словами; точная запись — модели в `backend/core/contracts/`. Если текст и код разошлись, прав код, а текст нужно поправить.

Контракт меняется только отдельной задачей с ADR (правило 2 в `CLAUDE.md`). Почему он устроен именно так — в ADR [0004](adr/0004-block-contract.md), [0005](adr/0005-pipeline-format.md) и [0006](adr/0006-backend-boundaries.md). Как состояние запуска лежит в базе — в ADR [0007](adr/0007-data-model.md).

| Часть контракта | Раздел | Файл в `backend/core/contracts/` |
| --- | --- | --- |
| Какие данные ходят между блоками | [1. Порты](#1-порты) | `ports.py` |
| Паспорт блока | [2. Манифест](#2-манифест) | `manifest.py` |
| Как движок вызывает блок | [3. run()](#3-run) | `run.py`, `screens.py` |
| Как записана схема урока | [4. Пайплайн](#4-пайплайн) | `pipeline.py` |
| Проверка, что всё стыкуется | [5. Проверка стыковки](#5-проверка-стыковки) | `wiring.py` |
| Что блок и движок получают извне | [6. Службы](#6-службы) | `interfaces.py`, `state.py` |

Примеры: 22 манифеста в `docs/examples/manifests/` и четыре сценария в `docs/examples/pipelines/`. Все они проверяются тестами в `tests/contracts/`.

## 1. Порты

Порт — вход или выход блока. У порта есть имя, подпись для редактора и тип данных.

### Тип данных

Тип складывается из трёх частей.

| Часть | Что значит | Как пишется в манифесте |
| --- | --- | --- |
| Вид | один из восьми видов данных | `type: Task` |
| Уточнение | что именно лежит в `Data` | `of: summary` |
| Список | один элемент или список | `list: true` |

Восемь видов:

| Вид | Что это | Главные поля |
| --- | --- | --- |
| `Event` | что запустило пайплайн | `trigger`, `occurred_at`, `student_id`, `assignment_id`, `payload` |
| `Task` | задача | `id`, `topic`, `difficulty`, `statement`, `check_method`, `answer`, `solution`, `tests`, `rubric` |
| `Answer` | ответ ученика | `task_id`, `form` (text, formula, code, photo), `text`, `file` |
| `Verdict` | результат проверки | `correct`, `score`, `max_score`, `comment`, `preliminary`, `task_id` |
| `Hint` | подсказка | `task_id`, `level` (1–3), `text` |
| `File` | ссылка на файл | `id`, `name`, `kind` (document, code, image, other), `media_type`, `student_id` |
| `Text` | текст | `text`, `source` |
| `Data` | всё остальное | форму описывает автор блока |

У первых семи видов форма жёстко задана контрактом. `Data` — общий вид для того, чего в списке нет: «конспект», «результат ученика», «сводка». Автор блока даёт такому виду имя-уточнение (`of: summary`) и может приложить его описание (`schema`). Новый вид данных появляется без изменения контракта.

Тип `Query` из рабочей записки убран: запрос Источника — это его настройки, а не входной порт.

### Правило совместимости

Выход можно подать на вход в двух случаях.

1. Типы совпадают целиком: вид, уточнение и «список или один».
2. Вход объявлен как `Data` без уточнения. Это значит «принимаю любое». Если такой вход ещё и список (`list: true`) — «принимаю любой список».

| Выход | Вход | Стыкуется | Почему |
| --- | --- | --- | --- |
| `Task` | `Task` | да | совпадают |
| `Task` | `Answer` | нет | разные виды |
| `Data<summary>` | `Data<submission>` | нет | разные уточнения |
| `Text` | `Data` | да | вход принимает любое |
| список `Task` | `Data` | да | вход принимает любое, в том числе список |
| `File` | список `Data` | нет | вход ждёт список |
| список `Task` | `Task` | нет | вход ждёт один элемент |
| `Data` | `Task` | нет | «неизвестно что» нельзя подать туда, где ждут задачу |

Функция — `can_connect(выход, вход)` в `ports.py`.

### Необязательный вход

Вход с `required: false` может остаться без данных. Пример: у блока «показать задачу» вход «подсказка» — при первом показе подсказки ещё нет.

### Вычисляемый тип выхода

У универсальных блоков тип выхода зависит от того, как блок используют. Тогда выход объявляется как `Data`, а настоящий тип вычисляется для каждого узла пайплайна.

| Запись | Что значит | Пример |
| --- | --- | --- |
| `same_as: items` | выход повторяет тип того, что подано на вход `items` | Подтверждение: что пришло на проверку, то и вышло |
| `from_config: result` | тип записан в настройке `result` узла | ИИ-обработка: в одном узле результат — «конспект», в другом — список задач |

### Соглашения о данных

- **Имён людей в данных нет.** Ученик обозначается идентификатором `student_id`.
- **Кому адресован результат.** Получатель берёт `student_id` из значения на входе `recipient` — например, из файла работы.
- **Свежесть.** На порту лежит последнее записанное значение. В цикле оно может остаться от прошлой задачи, поэтому у `Answer`, `Verdict` и `Hint` есть `task_id`: блок, которому это важно, сверяет его с текущей задачей.

## 2. Манифест

Манифест `block.yaml` — паспорт блока. Всё, что ядро и редактор знают о блоке, они берут отсюда.

| Поле | Обязательное | Что значит |
| --- | --- | --- |
| `id` | да | имя блока: `категория.название`, например `check.exact` |
| `version` | да | версия из трёх чисел: `0.1.0` |
| `name`, `description`, `author` | да | подписи для редактора |
| `category` | да | одна из семи категорий: `source`, `transform`, `student`, `check`, `ai_process`, `approval`, `sink` |
| `kind` | нет, по умолчанию `auto` | `auto` — выполняется сразу; `interactive` — ждёт ученика; `approval` — ждёт преподавателя |
| `screen` | для `interactive` и `approval` | какой готовый экран показать человеку (раздел 3) |
| `inputs`, `outputs` | нет | порты |
| `config` | нет | настройки блока в виде JSON Schema; по ней редактор строит форму |
| `outcomes` | нет, по умолчанию `[ok]` | исходы, по которым пайплайн выбирает следующий шаг |
| `runtime` | да | как блок запускается (ниже) |
| `tools` | нет | MCP-инструменты, разрешённые агенту внутри блока; только чтение |
| `side_effects` | нет, по умолчанию `false` | меняет ли блок что-то во внешнем мире: отправка письма, оценка в Moodle |

Категорий семь, а не восемь: Триггер — узел ядра, манифеста у него нет.

### Три способа запуска

| `runtime.type` | Что это | Поля | Полный пример |
| --- | --- | --- | --- |
| `python` | встроенный блок: функция в пакете Python | `entrypoint: blocks.student.show_task:run` | `student.show_task.yaml` |
| `mcp` | обёртка над инструментом MCP-сервера | `server: moodle`, `tool: get_submissions` | `source.moodle_submissions.yaml` |
| `http` | отдельный сервис | `url: http://sandbox:8000` | `check.code_tests.yaml` |

Для ядра разницы нет: все три вызываются одним и тем же `run()`.

- **python.** Ядро находит функцию по `entrypoint` и вызывает её.
- **mcp.** Ядро вызывает инструмент как обычную функцию. Аргументы — настройки узла и значения входов. Инструмент возвращает набор полей: имена совпадают с именами выходов, поле `outcome` — исход. Адрес сервера и ключ берутся из подключения преподавателя, в манифесте их нет.
- **http.** Сервис отвечает на `GET /manifest` своим манифестом и на `POST /run` результатом. Тело запроса — `{inputs, config, context}`, ответ — результат `run()` в JSON.

### Что проверяется при загрузке манифеста

- все обязательные поля заполнены, незнакомых полей нет — опечатка в названии поля будет ошибкой;
- имена входов, выходов и исходов не повторяются;
- блок, который ждёт человека, называет экран; экран подходит тому, кого ждут; у блока `auto` экрана нет;
- `same_as` ссылается на существующий вход, `from_config` — на существующую настройку;
- `config` — правильная JSON Schema.

Ошибка всегда называет поле и говорит, что не так: `id: обязательное поле не заполнено`.

## 3. run()

Блок — это одна функция. Она одинакова для всех трёх способов запуска.

```
run(inputs, config, context) -> результат
```

| Аргумент | Что в нём |
| --- | --- |
| `inputs` | значения входов: имя входа → значение |
| `config` | настройки узла; ссылки на параметры пайплайна уже заменены значениями |
| `context` | сведения о запуске и службы (ниже) |

### context

| Поле | Что значит |
| --- | --- |
| `run_id`, `node_id`, `pipeline_id` | какой запуск, какой узел, какой пайплайн |
| `params` | значения параметров пайплайна |
| `student_id`, `teacher_id` | чей запуск; только идентификаторы |
| `attempt` | номер попытки: упавший автоматический блок движок повторяет |
| `shown` | данные экрана, которые блок сам попросил показать; пусто при первом вызове |
| `human_response` | ответ человека с этого экрана; пусто при первом вызове |
| `llm` | ИИ-модель (раздел 6) |
| `tools` | MCP-инструменты, разрешённые блоку в манифесте (раздел 6) |

### Результат: «готово» или «жду человека»

**Готово** — блок отработал:

```json
{"status": "done", "outputs": {"verdict": {"correct": false}}, "outcome": "wrong", "events": []}
```

- `outputs` — значения выходов;
- `outcome` — исход, один из объявленных в манифесте;
- `events` — записи для журнала событий.

**Жду человека** — блоку нужен ответ ученика или преподавателя:

```json
{"status": "waiting", "screen": "answer_form", "data": {"task_id": "t1", "statement": "…", "forms": ["text"]}}
```

### Обмен «блок ждёт человека»

Блок не «висит» в ожидании. Обмен идёт в два вызова одной и той же функции.

1. Движок вызывает `run()`. В `context.shown` и `context.human_response` пусто.
2. Блок возвращает «жду человека»: какой экран показать и с какими данными.
3. Движок ставит запуск на паузу и сохраняет состояние в базу. Сервер можно перезапустить — урок не потеряется.
4. Человек отвечает на экране.
5. Движок вызывает тот же `run()` ещё раз с теми же входами и настройками. В `context.shown` лежат данные экрана из шага 2, в `context.human_response` — ответ человека.
6. Блок возвращает «готово».

Блок ничего не помнит между двумя вызовами — поэтому обмен одинаково работает для встроенного блока, MCP-сервера и HTTP-сервиса. Всё, что блоку понадобится после паузы, он кладёт в данные экрана и получает обратно в `context.shown`. Пример: блок распознавания фото при втором вызове берёт распознанный текст оттуда, а не обращается к модели заново — ученик подтверждал именно этот текст.

### Готовые экраны

Своего кода интерфейса у блока нет. Он выбирает один из четырёх экранов платформы.

| Экран | Для кого | Что показывает (`data`) | Что возвращает человек |
| --- | --- | --- | --- |
| `answer_form` | ученик | условие задачи, подсказку, допустимые формы ответа | ответ или просьбу о подсказке |
| `confirm_recognized` | ученик | фото и распознанный текст | «верно» или исправленный текст |
| `review_table` | преподаватель | таблицу: столбцы и строки | по каждой строке: оставить (с правками) или пропустить |
| `review_document` | преподаватель | один документ | «утверждаю» (с правками) или «отклоняю» |

В данных экрана `answer_form` есть только условие задачи. Ответа и эталонного решения там нет по самой форме данных, так что в браузер ученика они попасть не могут. Свободного чата тоже нет: ученик может только ответить или попросить подсказку.

Новый экран — это изменение контракта.

### Порты тьютора

Тьютор — блок `auto`. Он выдаёт одну подсказку и сам ученика не ждёт: подсказку показывает блок «показать задачу и принять ответ».

| Порт | Тип | Обязательный |
| --- | --- | --- |
| вход `task` | `Task` | да |
| вход `answer` | `Answer` | нет |
| вход `verdict` | `Verdict` | нет |
| вход `previous_hint` | `Hint` | нет |
| выход `hint` | `Hint` | — |

Исходы: `hint` — подсказка выдана, `give_up` — подсказать больше нечего. Уровень следующей подсказки на один выше, чем у прошлой подсказки по той же задаче.

## 4. Пайплайн

Пайплайн — файл JSON: параметры, узлы и переходы.

```json
{
  "format": 1,
  "id": "scenario_1_training",
  "name": "Тренировка с ИИ-тьютором",
  "params": [{"name": "topic", "title": "Тема", "type": "string"}],
  "nodes": [],
  "transitions": []
}
```

### Два вида связей

| Связь | На какой вопрос отвечает | Где записана |
| --- | --- | --- |
| Переход | что выполнять дальше | список `transitions` |
| Привязка входа | откуда взять данные | поле `inputs` узла |

Связей два вида, потому что это два разных вопроса. «Проверке» нужны задача от одного узла и ответ от другого, а выполняться она должна после ответа, а не после каждого из них.

### Параметры

Параметр — значение, которое преподаватель заполняет при назначении: тема, сложность, число задач. В настройках узла на параметр ссылаются так: `{"$param": "topic"}`. Поэтому один пайплайн «Тренировка» служит для всех тем.

### Узлы

| Вид узла | Что делает |
| --- | --- |
| `trigger` | старт пайплайна |
| `block` | выполняет блок |
| `switch` | развилка по значению |
| `for_each` | выполняет ветку для каждого элемента списка |

**Триггер.** В пайплайне ровно один узел-триггер. У него список способов запуска — один или несколько: `manual`, `student`, `schedule` (с полем `cron`), `moodle_event`. У триггера один выход — `event` типа `Event`.

```json
{"id": "start", "type": "trigger", "launches": [
  {"type": "moodle_event", "settings": {"poll_minutes": 5}},
  {"type": "schedule", "cron": "0 20 * * *"}
]}
```

**Блок.** Имя блока, настройки и привязки входов.

```json
{"id": "check_exact", "type": "block", "block": "check.exact",
 "inputs": {"task": "take_task.task", "answer": ["show.answer", "recognize.answer"]}}
```

**Развилка.** Исход узла — значение поля у данных. Пример: способ проверки записан в самой задаче, и развилка читает поле `check_method`.

```json
{"id": "by_method", "type": "switch", "value": "take_task.task", "field": "check_method"}
```

**«Для каждого».** Описан ниже.

### Привязка входа

Привязка — ссылка вида `узел.порт`. Вход читает последнее значение, записанное на этот выход.

- **Несколько ссылок на выбор.** `["show.answer", "recognize.answer"]` — берётся значение, записанное последним. Нужно там, где ветки сходятся: ответ пришёл либо из формы, либо после распознавания фото.
- **Поле записи.** `each_approved.item.task` — поле `task` у записи, собранной узлом «для каждого».

### Переходы

```json
{"from": "check_exact", "when": "wrong", "to": "tutor"}
```

- `when` — исход узла `from`. Переход без `when` срабатывает при любом исходе, для которого нет своего перехода.
- Из одного узла — не больше одного перехода на каждый исход. Узлы выполняются по одному; параллельно идут только элементы внутри «для каждого».
- Если подходящего перехода нет, ветка на этом заканчивается.

### Ограничитель цикла

Цикл — это переход назад. Чтобы он не стал бесконечным, у узла на его пути стоит ограничитель: сколько раз узел можно пройти.

```json
"limit": {"max": {"$param": "max_hints"}, "otherwise": "take_task", "reset_on": "take_task"}
```

| Поле | Что значит |
| --- | --- |
| `max` | сколько раз узел можно выполнить; число или параметр пайплайна |
| `otherwise` | куда идти, когда попытки кончились; не задано — ветка заканчивается |
| `reset_on` | счётчик обнуляется при каждом выполнении этого узла; не задано — один счётчик на весь запуск |

Пример читается так: «подсказку можно дать не больше `max_hints` раз на одну задачу; когда подсказки кончились — взять следующую задачу».

Ограничитель стоит у узла, а не у перехода: в узел «взять задачу» ведут пять разных переходов, а считать нужно их все вместе.

### «Для каждого»

```json
{
  "id": "each_work", "type": "for_each", "over": "get_works.works",
  "body": {"start": "by_kind", "nodes": [], "transitions": []},
  "collect": {
    "work": "each_work.item",
    "verdict": ["check_text.verdict", "check_code.verdict"],
    "comment": "comment.result"
  },
  "as": "graded_work"
}
```

| Поле | Что значит |
| --- | --- |
| `over` | список, который перебирается |
| `body` | тело: маленький граф, который начинается с узла `start` |
| `collect` | что собрать с каждого элемента |
| `as` | название записи, если собирается несколько полей |

У узла два выхода:

- `item` — текущий элемент; виден только внутри тела;
- `results` — список собранного; виден только снаружи.

Собрать можно одно значение (`"collect": "each.item.task"`) или запись из нескольких полей. Запись получает тип `Data` с уточнением из `as`, а её поля потом читаются как `узел.порт.поле` — с тем типом, с каким их собрали.

Правила видимости:

- узел внутри тела видит узлы снаружи;
- узел снаружи не видит узлы внутри тела — только `results`;
- если ветка элемента не дошла до конца и собрать нечего, элемент в `results` не попадает, в журнале остаётся запись.

## 5. Проверка стыковки

Функция `check_wiring(пайплайн, манифесты)` возвращает список ошибок. Пустой список — всё стыкуется. Каждая ошибка называет узел и говорит, что не так:

```
узел «show»: вход «task» ждёт Task, а «recognize.answer» выдаёт Answer
```

| Код | Что не так |
| --- | --- |
| `unknown_block` | блока нет среди манифестов |
| `unknown_input` | привязан вход, которого у блока нет |
| `missing_input` | обязательный вход ни к чему не привязан |
| `unknown_ref` | ссылка на узел, которого нет |
| `unknown_port` | ссылка на выход, которого у узла нет |
| `unknown_field` | у записи или у типа нет такого поля |
| `incompatible` | типы не стыкуются |
| `mixed_types` | ссылки на выбор выдают данные разных типов |
| `not_a_list` | «для каждого» перебирает не список |
| `nested_list` | с каждого элемента собирается список, а не одно значение |
| `record_name_taken` | запись названа так же, как данные одного из блоков пайплайна |
| `not_a_value` | развилка смотрит на список, а не на одно значение |
| `out_of_scope` | снаружи читается то, что видно только внутри «для каждого», или наоборот |
| `unknown_outcome` | переход по исходу, которого у узла не бывает |
| `bad_config_type` | в настройке не записан тип результата |
| `type_cycle` | тип выхода зависит сам от себя |

Чего эта проверка не делает — это работа валидатора (задача 06): достижимость узлов, ограничитель в каждом цикле, Подтверждение перед блоком с `side_effects`, запрет инструментов с последствиями у агента, соответствие настроек узла схеме `config`.

## 6. Службы

Блоку нужна ИИ-модель, движку — место, где хранить состояние. Но блок не подключает слой моделей, а движок — базу: иначе их нельзя тестировать и заменять по отдельности. Поэтому в контракте описаны только интерфейсы — что можно попросить.

| Интерфейс | Что умеет | Кто получает | Кто реализует |
| --- | --- | --- | --- |
| `LLMClient` | один вызов модели, при необходимости с ответом по схеме | блок — через `context.llm` | `backend/llm/` (задача 07) |
| `ToolClient` | список разрешённых MCP-инструментов и вызов инструмента | блок — через `context.tools` | `backend/mcp_client/` (задача 23) |
| `RunStore` | загрузить и сохранить состояние запуска, дописать события | движок — при создании | `backend/models/run_store.py` (задача 03) |

Настоящие реализации соединяет с ядром слой сборки — API и триггеры. В тестах вместо них подставляются простые подделки с тем же интерфейсом: фейковая модель, хранилище «в памяти».

**Состояние запуска** (`RunState`): статус, версия пайплайна, значения параметров, текущие узлы, последнее значение каждого выхода, счётчики ограничителей и то, чего запуск ждёт от человека.

## Четыре сценария

| Сценарий | Файл | Что в нём проверяет контракт |
| --- | --- | --- |
| 1. Тренировка | `scenario-1-training.json` | два вложенных цикла с ограничителями, пауза на ученике, развилка по способу проверки, несколько ссылок на выбор |
| 2. Проверка работ | `scenario-2-grading.json` | два способа запуска, «для каждого» с развилкой внутри, запись из нескольких полей, таблица на подтверждение, блоки с последствиями |
| 3. Материалы | `scenario-3-materials.json` | ИИ-обработка с разными типами результата, пара «ИИ решает — проверка сверяет», чтение поля записи |
| 4. Аналитика | `scenario-4-analytics.json` | запуск по расписанию, персональные сообщения, запасной канал: Telegram → почта → кабинет |

Что упрощено:

- **Сценарий 2, фото.** Сданное фото не обрабатывается: блок распознавания ждёт подтверждения ученика, а в этом сценарии ученика на платформе нет.
- **Сценарий 3, облако.** Лекция берётся из файла; Источник «облако» появится в задаче 30 и встанет на то же место.
- **Сценарий 1, счёт попыток.** В записке «три неудачи — задача проще». В пайплайне ограничитель считает подсказки: при трёх подсказках задача сменится после четвёртой неудачи, и просьба о подсказке без ответа тоже идёт в счёт. Как считать на самом деле — открытый вопрос 1, он решается до задачи 12; меняется это настройкой пайплайна, а не контрактом.
- **Сценарий 1, Telegram.** Итог уходит ученику без Подтверждения преподавателя — это его собственный результат. Считать ли это ошибкой или предупреждением, решается в задаче 06 (открытый вопрос 25).

Манифесты в `docs/examples/manifests/`, кроме трёх полных, — черновики: описание блока без кода. Когда блок будет написан, его манифест переедет в пакет блока.

## JSON Schema

Схемы манифеста и пайплайна лежат в `docs/schemas/`. По ним файл можно проверить без Python — например, в редакторе кода. Схемы выгружаются из моделей:

```
uv run python -m backend.core.contracts.schema_export
```

Тест `tests/contracts/test_schema_export.py` падает, если схемы отстали от моделей.
