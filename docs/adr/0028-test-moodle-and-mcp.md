# ADR 0028. Тестовый Moodle, MCP-сервер Moodle, MCP-клиент и подключения

- **Статус:** принято
- **Дата:** 11.11.2026

Дополняет ADR 0006 (кто реализует `ToolClient`) и ADR 0007 (таблица подключений). Модели в
`backend/core/contracts/` не меняются: в `docs/contract.md`, раздел 2, уточнено только, как
блок `mcp` передаёт файлы и как проверяется пометка «только чтение». Автор решил делать это
внутри задачи 23, без отдельной задачи по контракту.

## Контекст

Задача 23: работы из тестового Moodle должны попасть в пайплайн. Для этого нужны: Moodle, с
которым можно работать на Mac с Apple Silicon (открытый вопрос 12); MCP-сервер, который
читает работы; MCP-клиент в платформе; место, где хранятся адрес Moodle и токен
преподавателя; и способ вызвать блок `runtime: mcp`, который знает реестр. Отдельный вопрос
— как файл работы, который есть только в Moodle, становится ссылкой `File`, которую читают
следующие блоки (`transform.document_to_text` берёт содержимое через хранилище платформы).

## Решение

**Тестовый Moodle — `erseco/alpine-moodle` в отдельном `docker-compose.moodle.yml`.**
Образ собран для arm64, настраивается переменными окружения и ставит Moodle 5.3 сам при
первом запуске. Версия закреплена отпечатком образа. База — тот же `postgres:17`, что у
платформы, но отдельный контейнер. Отдельный файл, а не профиль в основном: Docker Compose
проверяет обязательные переменные во всём файле, и без паролей Moodle сломался бы обычный
`docker compose up` и CI. Moodle слушает только `127.0.0.1:8080`. Пароли администратора и
базы — в `.env`.

Проверены и отвергнуты: `bitnamilegacy/moodle` — работает на arm64, но больше не обновляется;
`moodlehq/moodle-docker` — набор для разработчиков Moodle, нужен исходный код Moodle рядом.

**Наполнение — `experiments/moodle_setup.py` и `experiments/moodle_seed.php`.** Скрипт PHP
выполняется внутри контейнера и пользуется генератором тестовых данных самого Moodle. Он
включает REST, создаёт сервис `platform` с тремя функциями чтения (`core_webservice_get_site_info`,
`mod_assign_get_assignments`, `mod_assign_get_submissions`), пользователя `platform_reader`
(преподаватель курса), курс, задание и четырёх выдуманных студентов: три сдачи (PDF, DOCX,
код) и один черновик. Повторный запуск ничего не дублирует. Токен скрипт отдаёт программе,
а на экран не печатает.

**MCP-сервер — `mcp_servers/moodle`, официальный SDK `mcp` 2.x.** Один инструмент
`get_submissions(course_id, assignment_id)` с пометкой `read_only_hint`. Он берёт только
сдачи со статусом «сдано», скачивает их файлы и возвращает `{works: [...], outcome}`:
`ok` или `empty`. Сервер ограничивает файл 10 МиБ, все файлы ответа — 50 МиБ. Вид файла
(`document`, `code`, `image`, `other`) он определяет по расширению. Имён из профиля
студента в ответе нет: Moodle не присылает их в этой функции, в `meta` — только номера в
Moodle. Но имя файла и содержимое работы приходят как есть, а в них студент может написать
свою фамилию («Иванов_лаба.docx»). Для ВКР это допустимо: Moodle только тестовый, данные
выдуманные, в пилоте Moodle не используется. До работы с настоящим Moodle нужно решить,
заменять ли имя файла нейтральным (открытый вопрос 30). Токен
уходит только на тот же сайт, что в подключении. Если Moodle прислал ссылку на файл с
другого адреса, файл не скачивается. Журнал httpx в сервере приглушён: он печатал адрес
файла вместе с токеном.

**Сервер запускается дочерней программой (stdio) на один вызов.** Адрес и токен он
получает в переменных окружения `MOODLE_URL` и `MOODLE_TOKEN` своего процесса. Отдельный
постоянный сервер не нужен, токены разных преподавателей не встречаются в одном процессе.
Цена — запуск Python на каждый вызов, около секунды. Для опроса раз в несколько минут
(задача 28) это допустимо.

**MCP-клиент — `backend/mcp_client/client.py`, класс `McpToolClient`.** Он реализует
`ToolClient` из контракта. При каждом вызове клиент спрашивает у сервера список
инструментов. Так он узнаёт пометку «только чтение» и схему входов. Отсюда два правила:

- блок без `side_effects` и агент (`call`) вызывают только инструменты с пометкой «только
  чтение»;
- инструмент получает только те значения, которые есть в его схеме: вход `event` блока
  Moodle сервер не принимает.

Ошибка сервера доходит до преподавателя текстом сервера, без служебного начала SDK. Отказ
поднимается после закрытия сессии: внутри неё SDK заворачивал отказ в группу исключений.
Агенту инструменты через `context.tools` начнёт выдавать задача 29.

**Подключения — таблица `connections`, миграция 0008.** У преподавателя одно подключение
каждого вида: блок называет только сервер (`moodle`), а адрес и токен берутся из подключения
преподавателя запуска. Токен шифруется Fernet (библиотека `cryptography`: шифрование и
проверка целостности вместе) ключом `PLATFORM_SECRET_KEY` из `.env`. В базе открытого
токена нет. Если ключ сменился, понятная ошибка просит создать подключение заново. Без
ключа платформа запускается, но подключения и блоки MCP недоступны: API отвечает 503,
в журнале предупреждение.

**API — `GET /api/v1/connections`, `PUT` и `DELETE /api/v1/connections/{kind}`.** Токен
принимается и не возвращается никогда. Адрес проверяется: `http` или `https`, без логина
и параметров в адресе. Формы в браузере пока нет: в пилоте Moodle не используется.

Ограничение: адрес может быть любым, в том числе `http` и внутренний адрес сервера. По
`http` токен идёт открытым текстом, а платформа сама обращается по адресу, который ввёл
преподаватель. Для тестового Moodle на `localhost` это нужно. Для настоящих сайтов правило
(например, `http` только для `localhost`, без внутренних адресов) вводится до формы
подключения в браузере (открытый вопрос 31).

**Блоки `mcp` — `backend/triggers/mcp_blocks.py`.** Способ вызова `mcp` передаётся реестру
так же, как `http`. Блок берёт подключение преподавателя запуска, вызывает инструмент и
превращает ответ в результат. Файл из ответа (`content_base64`) сохраняется через
`context.store.save_file` в файлы преподавателя. Ключ записи — отпечаток SHA-256 от порта,
имени, `meta` и содержимого, поэтому повтор блока не создаёт копий (ADR 0026). Дальше идёт
обычная ссылка `File`, а `meta` с номером студента в Moodle переносится в неё. Платформа не
доверяет серверу: она сама проверяет исход, лишние поля, base64 и размер файла.

**Блок `source.moodle_submissions`** — манифест из примеров без изменений. Пример пайплайна
— `docs/examples/pipelines/moodle-works-demo.json`.

## Проверка

- `tests/e2e/test_moodle_submissions.py`: подключение через API → ручной запуск →
  работы в пайплайне → текст документов в кабинете. Первый тест — на подделке Moodle,
  второй — на настоящем тестовом Moodle с сервером дочерней программой. Второй
  пропускается, если тестовый Moodle не запущен.
- Файл Moodle XML из задачи 22 (`sink.file`) импортирован в тестовый Moodle через импорт
  вопросов Moodle (`qformat_xml`). Создались два вопроса: «Короткий ответ» и «Эссе». HTML
  в условии экранирован, звёздочка в эталоне осталась буквальной (`3\*`).

## Последствия

- Закрыт открытый вопрос 12. Вопрос 11 (граница MCP и HTTP) остаётся открытым. Первый
  адаптер показал: MCP удобен там, где нужны подключение преподавателя и пометки
  инструментов. Для своих служб без подключений, как песочница, проще HTTP.
- В CI тестовый Moodle не поднимается: слишком тяжёлый (образ около 1,6 ГБ). Там идут тесты
  на подделке, а тест на настоящем Moodle запускается локально.
- Вид подключения пока один — `moodle`. Почта, Telegram и облако добавят свои виды и серверы
  в задачах 27 и 30. Имя сервера совпадает с видом подключения.
- Работа из Moodle не связана с учеником платформы: `student_id` пуст, номер в Moodle лежит
  в `meta`. Как адресовать результат студенту Moodle, решат задачи 27 и 28.
- «Обрабатывать только новые работы» и запуск по событию Moodle — задача 28. Пока каждый
  запуск берёт все сданные работы задания.
- Если потерять `PLATFORM_SECRET_KEY`, все подключения придётся создать заново.
