# ADR 0014. Хранилище платформы в `context` блока

- **Статус:** принято
- **Дата:** 14.10.2026

Меняет контракт: интерфейс `PlatformStore` в `backend/core/contracts/interfaces.py` и поле `store` в `RunContext` (`backend/core/contracts/run.py`). Закрывает открытый вопрос 24.

## Контекст

Блок не видит базу (ADR 0003, ADR 0006): он получает только то, что лежит в `context`, — модель и MCP-инструменты. Так блок можно проверить отдельно, на подделках.

Встроенным блокам «Источник: банк задач», «кабинет» и «результаты группы» нужны данные самой платформы. Первый из них появится в задаче 09: блок берёт из банка задачу нужной темы и сложности. Ни модель, ни MCP-инструменты ему в этом не помогут. Значит, в `context` нужна ещё одна служба, а это изменение контракта (ADR 0006, последствия).

## Варианты

**Как блок достаёт данные платформы.**

- (а) Блок сам открывает базу. Нарушает правило 4 и границы модулей: блок пришлось бы тестировать с PostgreSQL, а import-linter это запрещает.
- (б) Отдельный MCP-сервер «платформа», как у Moodle. Работает и для сетевых блоков, но ради чтения из своей же базы появляются лишний процесс, подключение и разбор ответов. MCP-инструменты в контракте — только для агентов внутри блока и только на чтение внешних систем.
- (в) Ещё один интерфейс в `context` — по образцу модели: в контракте только «розетка», реализация в `backend/models/`, подключает её слой сборки.

**Один интерфейс или по одному на вид данных** (задачи, результаты, кабинет).

- Один — меньше полей в `context`, одна подделка для тестов.
- По одному — точнее видно, чем пользуется блок, но сейчас нужен только банк задач.

## Решение

Вариант (в), один интерфейс `PlatformStore` — «хранилище платформы». Блок получает его через `context.store`.

Пока в нём два действия, оба только на чтение:

| Действие | Что делает |
| --- | --- |
| `find_tasks(topic, difficulty, subject)` | задачи банка по условиям; незаданное условие не учитывается; нет таких — пустой список |
| `get_task(task_id)` | одна задача по номеру или «нет такой» |

Отдаётся тип `Task` из контракта — тот же, что идёт по пайплайну.

Правила:

- **Доступ — только к своему.** Блок не называет преподавателя. Сборка выдаёт ему хранилище, которое уже ограничено преподавателем этого запуска (`context.teacher_id`). Чужие задачи блок не может запросить даже по ошибке в своём коде.
- **Только подтверждённые задачи.** Черновик в урок не попадает — так уже работает `TaskRepository.find`.
- **Выбор — дело блока.** Хранилище отвечает «какие задачи есть»; какую дать ученику и как подстроить сложность, решает блок.
- **Сетевые блоки хранилище не получают** — как и модель (ADR 0006): поле не попадает в тело запроса `POST /run`.
- **Для тестов** рядом с контрактом лежит подделка `FakeStore` (`backend/core/contracts/testing.py`): задачи в памяти, поиск тот же.

## Последствия

- Движок не меняется: хранилище в `context` добавляет обёртка блока в сборке, по образцу пометки вызовов модели (`_tagging` в `backend/triggers/assembly.py`, ADR 0013). Настоящее хранилище на базе и эту обёртку делает задача 09.
- В задаче 09 настоящее хранилище и в `get_task` должно отдавать только подтверждённые задачи: `TaskRepository.get` черновики не отсеивает. Номер, который не похож на номер задачи в базе, — это «нет такой», а не ошибка. На оба случая нужны тесты.
- Старые блоки и тесты ничего не замечают: без хранилища `context.store` пуст.
- Схемы в `docs/schemas/` не меняются: `RunContext` в них не входит.
- Каждое новое действие — запись в банк (Получатель «банк задач», задача 22), кабинет, результаты группы (задача 26) — снова изменение контракта отдельной задачей с ADR. Так интерфейс растёт только тем, что действительно понадобилось.
- Открыть свою задачу коллегам пока нельзя: банк у каждого преподавателя свой (решение автора по открытому вопросу 2, записывается в задаче 09). Если понадобится, меняется реализация хранилища, а не интерфейс.
