# ADR 0006. Границы внутри бэкенда: интерфейсы в контракте

- **Статус:** принято
- **Дата:** 12.10.2026

Дополняет ADR 0003: закрывает его пункт «границы внутри бэкенда пока не проверяются».

## Контекст

Модули должны знать друг о друге только через контракты (правило 4 в `CLAUDE.md`). В карте разработки было два противоречия с этим правилом (`docs/open-questions.md`, вопрос 22).

1. Блоки «зависят от LLM-слоя», но по ADR 0003 блок не видит ничего, кроме контрактов. Как тогда тьютор вызывает модель?
2. Движок «тестируется без БД», а задача 04 требует «состояние в БД». Как движок сохраняет состояние, не подключая базу?

## Варианты

(а) Разрешить блокам подключать `backend/llm/`, а движку — `backend/models/`. Просто, но блок перестаёт быть плагином: его нельзя проверить без настоящего слоя моделей, а сторонний блок окажется привязан к внутренностям платформы.

(б) Описать в контракте только интерфейсы — что можно попросить, — а готовые реализации передавать блоку и движку снаружи.

## Решение

Вариант (б). В `backend/core/contracts/` лежат три интерфейса:

| Интерфейс | Кто пользуется | Кто реализует |
| --- | --- | --- |
| `LLMClient` — вызов модели | блок, через `context.llm` | `backend/llm/` |
| `ToolClient` — MCP-инструменты, разрешённые блоку | блок, через `context.tools` | `backend/mcp_client/` |
| `RunStore` — состояние запуска и журнал событий | движок, получает при создании | `backend/models/` |

Соединяет всё **слой сборки** — `backend/api/` и `backend/triggers/`: он создаёт настоящие реализации и передаёт их движку. Только ему разрешено подключать весь бэкенд.

Границы записаны двумя новыми правилами в `.importlinter` и проверяются в CI:

5. Слой ИИ-моделей, MCP-клиент и модели базы видят только контракты — ни ядро, ни API, ни друг друга.
6. Ядро (движок, реестр, валидатор) не подключает слой ИИ-моделей, MCP-клиент, модели базы, API и триггеры.

Тесты в `tests/test_import_rules.py` проверяют оба правила на пробном проекте.

## Последствия

- Таблица модулей в карте уточнена: блоки зависят только от контрактов; появилась строка «слой сборки».
- Движок тестируется с хранилищем «в памяти», без базы. Требование задачи 04 «состояние в БД» выполняет реализация `RunStore` на PostgreSQL, она проверяется отдельным тестом на тестовой базе.
- Блок тестируется с фейковой моделью. Блоки не видят `backend/llm/`, поэтому фейковая модель будет лежать рядом с контрактом — `backend/core/contracts/testing.py`. Она появится в задаче 07; это вспомогательный файл для тестов, модели контракта он не меняет.
- Нужная блоку служба, которой нет в `context`, — это изменение контракта. Уже известен один такой случай: встроенным блокам «банк задач» и «кабинет» нужен доступ к данным платформы. Это открытый вопрос 24, он решается до задачи 09.
- Модель состояния запуска (`RunState`) описана минимально. Если в задаче 04 её придётся уточнить — отдельной ADR.
- При вызове блока по сети (`mcp`, `http`) службы не передаются: сервис сам решает, какой моделью пользоваться.
