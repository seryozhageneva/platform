# ADR 0013. API v1 и триггер «вручную»

- **Статус:** принято
- **Дата:** 13.10.2026

Контракт, движок, реестр, валидатор и таблицы базы не меняет. Закрывает открытый вопрос 28.

## Контекст

Движок, хранилище, реестр, валидатор и слой моделей готовы (ADR 0008–0012), но встречались только в тестах. Задача 08 впервые соединяет их в работающий сервер: это слой сборки из ADR 0006 — API (`backend/api/`) и триггеры (`backend/triggers/`).

Документы оставили на эту задачу шесть вопросов:

1. выполняется запуск прямо в запросе или в фоновой очереди (ADR 0008 и 0010 ждали очередь в задаче 08);
2. как сервер узнаёт, кто спрашивает, если вход появится только в задаче 13;
3. кто помечает вызов модели запуском и узлом (открытый вопрос 28);
4. где вызывается валидатор (ADR 0011: «при сохранении и перед запуском»);
5. кто проверяет значения параметров запуска (ADR 0011 оставил это задаче 08);
6. в каком виде сервер сообщает об отказе.

## Варианты

**Где выполняется запуск.** (а) Фоновая очередь arq: запрос отвечает сразу, запуск выполняет отдельный рабочий процесс. (б) Прямо в запросе: ответ приходит, когда запуск закончился, встал на паузу или упал.

**Кто спрашивает.** (а) Сделать вход уже сейчас. (б) Вообще не различать преподавателей до задачи 13. (в) Временно: запрос сам называет преподавателя.

**Пометка вызова модели.** (а) Слой сборки создаёт движок с моделью, помеченной запуском; узел остаётся пустым. (б) Изменить движок: дать ему способ выдать блоку модель с пометкой узла. (в) Слой сборки оборачивает функцию каждого блока и подменяет модель в `context`.

## Решение

### Запуск выполняется в запросе; очередь — отдельная задача 18a

Вариант (б). Запрос `POST /pipelines/{id}/runs` вызывает движок и отвечает состоянием запуска. Для сценария 1 это естественно: ученик отправил ответ и ждёт следующего экрана.

Очередь нужна, когда запуск долгий — проверка работ всей группы, подготовка материалов по лекции. Это сценарии 2 и 3, поэтому очередь вынесена в задачу **18a** перед ними. Вместе с очередью задача 08 принесла бы второй процесс, третью библиотеку и Redis в тестах — больше одного дня.

Форма ответа выбрана так, чтобы очередь её не изменила: в ответе есть статус, и после появления очереди он сможет быть «выполняется». Клиент уже сейчас должен читать состояние отдельным запросом `GET /runs/{id}`.

### Кто спрашивает — временно по заголовку

Вариант (в). Запрос называет преподавателя в заголовке `X-Teacher-Id`; сервер проверяет, что такой человек есть и он преподаватель или администратор. Пароля нет, то есть сервер верит запросу на слово. Поэтому он слушает только свой компьютер (`127.0.0.1`) и из сети не виден.

Всё решение — одна функция `current_teacher` в `backend/api/deps.py`. Задача 13 заменит её настоящим входом, эндпоинты при этом не меняются. Вариант (б) не годился: правило «каждый видит только своё» (ADR 0007) должно работать и проверяться тестами уже сейчас.

### Пометку вызова модели ставит слой сборки

Вариант (в). В `context`, который движок передаёт блоку, уже есть `run_id` и `node_id`. Сборка (`backend/triggers/assembly.py`) оборачивает функцию каждого блока: перед вызовом заменяет в `context` модель на ту же модель с пометкой — методом `bound(run_id, node_id)` из ADR 0012. Вызов попадает в журнал `llm_calls` и с запуском, и с узлом.

Движок и контракт не меняются. Вариант (а) оставлял узел пустым, а он нужен, чтобы посчитать, сколько стоит каждый блок (задача 32). Вариант (б) менял движок ради того, что слой сборки умеет сам.

### Сборка — один объект для API и будущих триггеров

`Assembly` держит репозитории, хранилище запусков, реестр блоков и модель и выдаёт движок. Лежит в `backend/triggers/`, а не в `backend/api/`: рабочему процессу очереди и триггеру «расписание» она понадобится без сервера. Триггеры API не подключают.

### Валидатор — при сохранении и перед запуском

- `POST /pipelines` и `PUT /pipelines/{id}`: с ошибкой пайплайн не сохраняется, с предупреждением — сохраняется, предупреждения уходят в ответе.
- Перед запуском пайплайн проверяется заново по текущим блокам: блок могли обновить или убрать после сохранения (ADR 0011).

### Что проверяется перед запуском

По порядку, до первой находки:

| Код | Что не так |
| --- | --- |
| `launch_not_allowed` | у узла-триггера нет способа запуска «вручную» |
| коды валидатора | пайплайн перестал проходить проверку |
| `block_not_callable` | блок известен, но вызвать его нечем (`mcp` и `http` без способа вызова) |
| `bad_param` | лишний параметр, незаполненный параметр или значение не того типа |

Тип значения сверяется тем же правилом, что и значение по умолчанию в контракте (`Param`). «Не число» и бесконечность числом не считаются: база их не хранит (ADR 0007). Отказ запуска не создаёт. Запуск вручную всегда берёт последнюю версию пайплайна; каждый запрос — новый запуск.

### Отказ — всегда в одном виде

`{"message": "...", "problems": [{"node": ..., "code": ..., "message": ...}]}` — текст по-русски и список причин. Так же выглядят запрос не по формату, неизвестный адрес и неверный метод. Ошибки разбора переводятся в те же строки, что и при чтении файла пайплайна (`explain` из контракта); редкая ошибка, для которой перевода там нет, приходит фразой библиотеки по-английски. Незнакомое поле в теле запроса — отказ, а не молчаливый пропуск. Данные, которые база не записывает, — например, нулевой символ в тексте из PDF — тоже отказ 422, а не сбой сервера; текст ошибки базы в ответ не попадает.

| Код ответа | Когда |
| --- | --- |
| 401 | не сказано, кто спрашивает, или такого преподавателя нет |
| 404 | записи нет среди своих — чужая запись выглядит так же, как несуществующая |
| 422 | запрос не принят: причины в `problems` |

### Что отдаёт `GET /runs/{id}`

Статус, версию пайплайна, параметры, текущий узел, чего ждёт запуск и текст ошибки. Значений портов в ответе нет: в них будут ответы учеников, и что из них показывать, решает кабинет (задача 17).

## Последствия

- Критерий «пайплайн запускается запросом, события видны в журнале» закрыт тестом `test_pipeline_is_started_by_a_request_and_events_are_in_the_journal` в `tests/api/test_runs_api.py` и ручной проверкой `uv run python -m experiments.api_check`.
- Открытый вопрос 28 закрыт; тест — `test_model_calls_are_tagged_with_run_and_node`.
- Пока нет очереди, долгий запуск держит запрос открытым. Нужна ли пауза между повторами упавшего блока (ADR 0008, 0010), решается в задаче 18a.
- Сервер нельзя открывать в сеть до задачи 13: заголовку `X-Teacher-Id` может назваться кто угодно. Деплой — задача 24, после входа.
- Настоящих блоков ещё нет, поэтому тесты API работают на фейковых блоках из временной папки, а ручная проверка — на пайплайне из триггера и развилки.
- Сервер не стартует, если в `.env` не выбран `LLM_PROVIDER` или не задан адрес базы; причина печатается одной строкой.
- Реестр читается один раз при старте сервера (ADR 0011): новый блок виден после перезапуска. Блоки, которые не загрузились, перечисляются в журнале сервера.
- Ответ на паузе (`respond`), продолжение после ошибки (`resume`), список запусков и список блоков для редактора — задачи 10, 16 и 17.
- Новые библиотеки: `fastapi` и `uvicorn`. Тестовый клиент FastAPI предупреждает, что библиотека `httpx` для него устарела и её сменит `httpx2`; тесты проходят, замена — отдельным решением автора.
- В репозитории появился `.claude/launch.json`: по нему Claude Code поднимает сервер в своём браузере.
