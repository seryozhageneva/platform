# ADR 0023. Файлы платформы в хранилище блока

- **Статус:** принято
- **Дата:** 10.11.2026

Меняет контракт: в интерфейсе `PlatformStore` (`backend/core/contracts/interfaces.py`) два новых действия. Дополняет ADR 0014.

## Контекст

Тип `File` в контракте — ссылка на файл: номер, имя, вид, тип содержимого, размер, ученик. Самого содержимого в ней нет, и так задумано: пайплайн передаёт между узлами ссылки, а не мегабайты.

В задаче 19 появляются блоки «Источник: файл» и «Преобразование: документ → текст». Первому нужно по номеру из настроек получить описание файла, второму — прочитать байты PDF или DOCX. В `context` блока ни того ни другого нет. У платформы нет и места, где лежат загруженные файлы.

## Варианты

**Как блок получает файл.**

- (а) Новые действия в хранилище платформы `context.store`. Хранилище уже ограничено преподавателем запуска (ADR 0014), подделка для тестов уже есть.
- (б) Отдельная служба `context.files`. Точнее видно, кто пользуется файлами, но ещё одно поле в `context` и ещё одна подделка. ADR 0014 уже выбрал один интерфейс на все данные платформы.
- (в) Класть содержимое прямо в значение `File`. Ломает смысл типа, раздувает состояние запуска в базе и журнал.

**Где лежит содержимое файла.**

- (а) В PostgreSQL, в той же таблице, что и описание. Одна база, одна резервная копия; права проверяются тем же запросом; запись описания и содержимого — одна транзакция.
- (б) В папке на диске сервера, в базе — только путь. Базе легче на больших файлах, но нужны отдельный том Docker, отдельное копирование и согласование «запись в базе есть — файла нет».
- (в) Объектное хранилище (S3-совместимое). Для платформы одной школы — лишний сервис.

## Решение

Вариант (а) в обоих вопросах. В `PlatformStore` два действия, оба только на чтение:

| Действие | Что делает |
| --- | --- |
| `get_file(file_id)` | описание файла — тип `File` из контракта — или «нет такого» |
| `read_file(file_id)` | содержимое файла (байты) или «нет такого» |

Описание и содержимое разделены: «Источнику» хватает описания, и тянуть байты ради него незачем.

Файлы лежат в новой таблице `files`: владелец-преподаватель, ученик (если это его работа), имя, вид, тип содержимого, размер и само содержимое. Номер строки — это поле `id` у `File` в пайплайне.

Правила:

- **Доступ — только к своему.** Хранилище, как и для задач, ограничено преподавателем запуска: чужой файл — это «нет такого».
- **Странный номер — «нет такого», а не ошибка.** Как у `get_task`.
- **Размер всегда равен длине содержимого** — за этим следит сама база.
- **Описание не тянет содержимое:** столбец с байтами загружается только по `read_file`.
- **Подделка** `FakeStore` принимает файлы парами «описание — содержимое» и отдаёт их по номеру.

## Последствия

- Движок не меняется: хранилище по-прежнему кладёт в `context` обёртка блока в сборке, теперь с репозиторием файлов.
- Сетевые блоки (`mcp`, `http`) файлов через хранилище не получают — как и всего хранилища (ADR 0014).
- Загрузку файла преподавателем (API) и ограничение размера делает задача 19. Блоки не пишут файлы: запись через блок — снова изменение контракта.
- Хранить в базе большие файлы неудобно. Учебные документы — единицы мегабайт, поэтому сейчас это не мешает. Если понадобится папка или S3, меняется реализация хранилища, а не контракт.
- Работы учеников в `submissions` по-прежнему хранят ссылку `File`; содержимое — в `files`.
- Схемы в `docs/schemas/` не меняются: `RunContext` в них не входит.
