# ADR 0029. Сквозные сценарии 2 и 3: извлечение кода и выбор полей для модели

- **Статус:** принято
- **Дата:** 11.11.2026

Дополняет ADR 0024 (ИИ-обработка), ADR 0025 (песочница) и ADR 0028 (работы из Moodle).
Модели в `backend/core/contracts/` не меняются: меняются только манифесты двух блоков и
примеры пайплайнов.

## Контекст

Задача 24 из карты разбита на две. В части 24 нужно, чтобы сквозные тесты сценариев 2 и 3
были зелёными. Деплой на VPS вынесен в задачу 24a: для него автор должен выбрать и оплатить
сервер (открытый вопрос 13).

Для этих тестов не хватало трёх вещей:

1. В сценарии 2 программа студента проверяется тестами в песочнице, но блока
   `transform.extract_code`, который превращает файл с кодом в ответ, не было: был только
   черновик манифеста. Песочница принимает ответ, только если номер задачи в нём совпадает
   с задачей, по тестам которой она проверяет (ADR 0025). Из самого файла этот номер не
   узнать.
2. В сценарии 3 узел «Решить независимо» получал задачу целиком, вместе с эталоном и
   решением (замечание в ADR 0024). Совпадение его ответа с эталоном ничего не доказывало.
3. В сценарии 2 преподаватель правит комментарий в таблице. Таблица разрешает править
   только текстовые ячейки, а комментарий в примере был записью `Data` неизвестного вида.

## Решение

**Блок `transform.extract_code`.** Входы: файл (`File`) и задача (`Task`). Выход: ответ
(`Answer`) формы `code` с номером этой задачи и текстом программы. Блок берёт содержимое
через хранилище платформы. Файл не вида `code`, файл больше 1 МиБ, пустой или не в UTF-8
дают исход `unreadable` и событие `code_unreadable` с причиной, а не ошибку запуска. Метка
порядка байтов в начале файла убирается. Лимит размера программы проверяет сама песочница:
блок отсекает только то, что явно не программа.

**Настройка `data_fields` у `ai_process.generate`.** Это список полей исходных данных,
которые увидит модель. У записи остаются только эти поля, у списка записей — эти поля у
каждой записи. Если данные не запись, блок выдаёт ошибку. В сценарии 3 узел «Решить
независимо» получает `["id", "statement"]`: номер нужен ответу, условие — для решения. Из
промпта убрана фраза «не глядя на эталон»: эталона там больше нет.

**Комментарий в сценарии 2 — `Text`.** Узел «Написать комментарий» возвращает `Text`, а
таблица разрешает править `comment.text`. Будущие получатели «оценки в Moodle» и «email»
принимают `Data` без уточнения, то есть любые данные, так что для них ничего не меняется.

**Тест сценария 2 собирает пайплайн из примера.** Тест берёт `scenario-2-grading.json`,
заменяет способы запуска на ручной и отрезает последний цикл «оценка в Moodle и письмо».
Запуск по событию и по расписанию появится в задачах 25 и 27, получатели Moodle и email — в
задачах 26 и 27. Пример остаётся полным образцом сценария. Тест идёт в двух вариантах: на
подделке Moodle (всегда) и на тестовом Moodle в Docker (если он запущен). Песочница
работает в том же процессе, а контейнер с программой заменён подделкой, как в задаче 21.

## Последствия

- В одной задаче банка лежат и рубрика для текстовых работ, и тесты для программ. Способ
  проверки у такой задачи — `code`; рубрика при этом используется блоком проверки по
  рубрике, который способ проверки не смотрит.
- `data_fields` — общий механизм: им можно скрыть от модели любые поля, например номер
  студента в Moodle. Если поле не указано, модель его не увидит.
- Узнать, к какой задаче относится работа, по-прежнему можно только из пайплайна: задача
  приходит из банка по номеру в параметрах запуска.
