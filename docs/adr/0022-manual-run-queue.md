# ADR 0022. Фоновый ручной запуск

- **Статус:** принято
- **Дата:** 10.11.2026
- **Задача:** 18a; меняет поведение ручного старта из [ADR 0013](0013-api-v1-manual-trigger.md).

## Решение

`POST /api/v1/pipelines/{id}/runs` проверяет права, последнюю версию и параметры, как раньше.
Успешный ответ `201` содержит прежний объект запуска со статусом `running`. Этот статус
означает и ожидание в очереди, и выполнение. За состоянием и журналом кабинет обращается
к прежним адресам. Ответы преподавателя на паузе и работа кабинета ученика выполняются
в запросе. Контракты и таблицы не меняются.

PostgreSQL хранит состояние, параметры, версию и журнал. API одной транзакцией записывает
запуск и `run_queued`, а перед подтверждением транзакции отправляет задание в Redis.
Задание в формате JSON несёт только идентификатор запуска; он же служит ключом arq.
Если Redis не подтвердил приём за две секунды, API откатывает транзакцию и возвращает
`503` с кодом `queue_unavailable`. Если задание всё-таки попало в Redis, рабочий процесс
не найдёт принятого запуска и пропустит его. Это же правило действует, если отправка
удалась, а PostgreSQL откатил транзакцию. Если ответ API потерялся, преподаватель
сначала проверяет список запусков: транзакция могла успеть завершиться.

Перед чтением запуска рабочий процесс берёт ту же блокировку PostgreSQL по идентификатору,
что и API при его создании. Так он ждёт подтверждения или отката транзакции. Он загружает
сохранённую версию пайплайна, отмечает `run_started` до вызова блоков и держит блокировку
до остановки движка. При повторной доставке уже начатый или остановленный запуск
пропускается. На весь вызов движка отводится 15 минут. Обрабатываемый сбой рабочего
процесса останавливает ещё активный запуск со статусом `error` и событием
`worker_failed`, если PostgreSQL доступен.

Повторять всё задание автоматически опасно: некоторые блоки выполняют внешнее действие,
которое могло уже состояться. Повторы отдельных автоматических блоков остаются как в
[ADR 0010](0010-engine-v2.md): без новой задержки между попытками.

## Запуск и разбор сбоев

```sh
docker compose up -d --wait postgres redis
uv run python -m backend.api
uv run arq backend.triggers.worker.WorkerSettings
```

Две последние команды работают в отдельных терминалах. API и рабочий процесс используют
один `REDIS_URL` (по умолчанию `redis://127.0.0.1:6379/0`). Используй адрес вида
`redis://хост:порт/номер` или `rediss://хост:порт/номер`, без параметров после `?`.
Для ручной проверки можно
запустить `uv run python -m experiments.api_check` на выдуманных данных.

- Если в журнале есть только `run_queued`, проверь, запущен ли рабочий процесс и видит ли он
  Redis. Потеря данных Redis или истечение срока задания может оставить такой запуск без
  исполнителя.
- Если есть `run_started`, но статус долго остаётся `running`, проверь журнал рабочего
  процесса по идентификатору запуска. После жёсткой остановки или потери связи с базой запись
  о сбое может отсутствовать. Автоматического восстановления таких запусков в 18a нет:
  прежде чем запускать заново, нужно выяснить, успели ли блоки выполнить внешние действия.
