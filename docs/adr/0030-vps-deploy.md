# ADR 0030. Платформа на сервере: контейнеры, Caddy и HTTPS

- **Статус:** принято
- **Дата:** 11.11.2026

Дополняет ADR 0013 (сервер API), ADR 0019 (вход и cookie), ADR 0022 (очередь) и ADR 0025
(песочница). Модели в `backend/core/contracts/` не меняются.

## Контекст

Задача 24a закрывает гейт 2: платформа открывается по адресу. До неё всё запускалось на
компьютере автора пятью командами в разных терминалах, а API слушал только `127.0.0.1`.
На сервере нужно:

- запускать всё одной командой и поднимать заново после перезагрузки;
- открыть из интернета только сайт, а базу, Redis, API и песочницу оставить внутри;
- включить HTTPS: без него пароль преподавателя и cookie входа идут открытым текстом;
- не хранить в публичном репозитории домен, адрес сервера и пароли (правило 10).

Сервер, домен и провайдер ещё не выбраны (открытый вопрос 13). Поэтому всё должно сначала
проверяться на компьютере автора.

## Решение

**Один файл Compose для сервера — `docker-compose.prod.yml`.** В нём база, Redis, миграции,
API, рабочий процесс, песочница и Caddy. Это отдельный файл, а не дополнение к
`docker-compose.yml`: у файла для разработки база открыта на `127.0.0.1:5432` для тестов, а
на сервере её порт не открыт вовсе. Миграции — отдельный контейнер, который выполняет
`alembic upgrade head` и завершается; API и рабочий процесс ждут его успешного окончания.

**Один `Dockerfile`, три образа.** `platform` — Python-код с библиотеками из `uv.lock`, без
библиотек для разработки, работает не от имени администратора. Из него с разными командами
запускаются миграции, API и рабочий процесс. `sandbox` — тот же код и программа `docker`.
`web` — Caddy и собранный фронтенд. Секреты в образы не попадают: `.env` и `certs/`
исключены в `.dockerignore` и подключаются к контейнерам при запуске.

**Caddy — обратный прокси и HTTPS.** Caddy выбран вместо nginx и certbot, потому что сам
получает и продлевает сертификат Let's Encrypt и сам перенаправляет `http://` на `https://`.
Его настройки — десяток строк в `deploy/Caddyfile`. Наружу открыт только `/api/…`, страницы
`/docs` и `/openapi.json` остаются внутри. Фронтенд и API открываются с одного адреса, как и
предполагал ADR 0019, поэтому проверка источника и cookie с `SameSite=Lax` работают без
изменений. Домен приходит из переменной `PLATFORM_DOMAIN` в `.env` на сервере. Для
`localhost` Caddy выпускает сертификат своим удостоверяющим центром — так HTTPS проверяется
на компьютере автора.

**API за прокси.** Браузер приходит к Caddy по HTTPS, а Caddy к API — по HTTP внутри Docker.
Без поправки API считал бы каждый запрос HTTP: cookie входа не получала бы пометку `Secure`,
а проверка источника отклоняла бы вход, потому что браузер присылает `Origin: https://…`.
Поэтому `python -m backend.api` читает две настройки: `PLATFORM_API_HOST` (где слушать) и
`PLATFORM_TRUSTED_PROXIES` (чьему заголовку `X-Forwarded-Proto` верить). По умолчанию обе —
`127.0.0.1`, то есть на компьютере автора ничего не меняется. На сервере API слушает
`0.0.0.0` и верит всем: его порт не открыт наружу, достучаться до него могут только соседние
контейнеры, а заголовки ставит Caddy, затирая присланные браузером.

**Песочница получает Docker сервера.** Она по-прежнему запускает одноразовые контейнеры с
программами учеников через команду `docker` (ADR 0025), поэтому к её контейнеру подключён
`/var/run/docker.sock` и она работает от имени администратора. Образ
`platform-code-runner:local` для программ учеников собирается заранее отдельной командой.

**Проверка гейта — `experiments/deploy_check.py`.** Скрипт открывает страницу, `/api/v1/health`,
проверяет перенаправление на HTTPS и то, что `/docs` не виден; с `--email` — вход
преподавателя и пометки `Secure` и `HttpOnly` у cookie. Проверка сертификата не отключается:
для `localhost` скрипт получает корневой сертификат Caddy через `--ca-file`.

## Последствия

- Инструкция для сервера — `docs/deploy.md`. Она одна для репетиции на компьютере и для VPS.
- Доступ к `docker.sock` равен правам администратора сервера. Взлом песочницы — это взлом
  всего сервера. Сама песочница принимает запросы только изнутри Docker, а программы
  учеников запускаются без сети и с ограничениями (ADR 0025). Отдельный сервер или
  rootless Docker для песочницы — возможное улучшение, в ВКР описывается как ограничение.
- Тестовый Moodle на сервер не ставится: работы из Moodle проверены на компьютере автора.
- Нет резервных копий базы, наблюдения за сервером и автоматического обновления из GitHub.
  Обновление — `git pull` и та же команда запуска.
- Заголовок HSTS («всегда только HTTPS») пока не включён: на `localhost` он мешал бы другим
  локальным сайтам автора, например тестовому Moodle на `http://localhost:8080`.
