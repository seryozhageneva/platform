# ADR 0015. Банк задач: API и выбор задачи для урока

- **Статус:** принято
- **Дата:** 14.10.2026

Контракт, движок и таблицы базы не меняет. Закрывает открытый вопрос 2.

## Контекст

В ADR 0014 появился интерфейс хранилища платформы `PlatformStore`, но за ним было пусто. Задача 09 добавляет три вещи: настоящее хранилище на базе, первый настоящий блок «Источник: банк задач» и API, через которое преподаватель наполняет банк.

Документы оставили на эту задачу пять вопросов:

1. общий банк у преподавателей одной установки или у каждого свой (открытый вопрос 2);
2. кто и как кладёт хранилище в `context` блока;
3. как блок выбирает задачу и подстраивает сложность: в манифесте сказано только «после неудачи — проще, после успеха — та же или выше»;
4. в каком статусе появляется задача, созданная через API;
5. что делать с подтверждённой задачей, которую нечем проверить.

## Решение

### Банк у каждого преподавателя свой

Решение автора: задача принадлежит тому, кто её создал, и видна только ему. Так уже устроена таблица `tasks` (ADR 0007). Открыть свою задачу коллегам пока нельзя. Если это понадобится, изменится реализация хранилища, а не интерфейс (ADR 0014).

### Хранилище кладёт в `context` обёртка блока в сборке

`Assembly` оборачивает функцию каждого блока (`_serviced` в `backend/triggers/assembly.py`). Перед вызовом обёртка кладёт в `context` службы этого запуска:

- модель с пометкой запуска и узла — так было и раньше (ADR 0013, прежнее имя обёртки — `_tagging`);
- хранилище `PgPlatformStore` (`backend/models/platform_store.py`), привязанное к преподавателю запуска (`context.teacher_id`).

Если у запуска нет преподавателя, хранилище не выдаётся: ограничить его было бы некем. Движок и контракт не меняются.

Хранилище отдаёт только свои и только подтверждённые задачи, в том числе в `get_task`. Номер, который не похож на номер задачи в базе, — это «нет такой», а не ошибка (ADR 0014, «Последствия»).

### Как блок выбирает задачу

| Что подано | Какая сложность |
| --- | --- |
| настройка `task_id` | эта задача; нет такой — исход `empty` |
| ничего, или подстройка выключена (`adapt: false`) | стартовая (`difficulty` из настроек) |
| прошлая задача и вердикт «верно» | сложность прошлой + 1 |
| прошлая задача и вердикт «неверно» | сложность прошлой − 1, но не ниже 1 |

- Если на новой сложности задач нет, остаётся сложность прошлой задачи. Если нет и там — исход `empty`. Отсюда «та же или выше» из манифеста.
- Стартовая сложность строгая: если на ней задач нет, блок не подбирает другую сам, а сообщает `empty`. В журнале появляется событие `no_tasks` с темой и сложностью: преподаватель видит, чего не хватает в банке.
- Вердикт, у которого `task_id` не совпадает с прошлой задачей, подстройку не включает.
- Из подходящих задач блок выбирает случайную, но не прошлую, если есть другие. Генератор случайных чисел зависит от номера запуска и прошлой задачи: повтор упавшего блока (ADR 0010) выбор не меняет, а тесты предсказуемы.
- О выборе блок пишет в журнал событие `task_chosen`: номер задачи, сложность и причину (`start`, `harder`, `easier`, `same`, `task_id`). Имён учеников там нет. Из этих событий задача 32 посчитает, как менялась сложность.

Задача 15 вернётся к одному ограничению. Блок помнит только прошлую задачу, поэтому за урок задача может повториться, но не подряд. Чтобы не повторять задачи за весь урок, блоку нужна история запуска. Её в `context` нет, и это было бы изменение контракта.

Сколько неудач должно пройти до задачи попроще — это открытый вопрос 1 (задача 12). Его решает граф: когда звать блок банка снова. Блок только отвечает на вердикт, который пришёл.

### API банка задач

`POST /api/v1/tasks`, `GET /api/v1/tasks` (фильтры по предмету, теме, сложности и статусу), `GET /api/v1/tasks/{id}`, `PUT /api/v1/tasks/{id}`. Чужая задача выглядит как несуществующая (404), как у пайплайнов (ADR 0013).

- **Задача из API по умолчанию подтверждена**: её пишет сам преподаватель. Черновики нужны для задач, которые сочинил ИИ; их запишет Получатель «банк задач» (задача 22). Черновик можно создать явно, `"status": "draft"`, а подтвердить его через `PUT`.
- **Подтверждённую задачу должно быть чем проверить**: у краткого ответа — `answer`, у кода — `tests`, у развёрнутого решения — `rubric`. Иначе проверка в уроке упадёт. Черновик может быть неполным.
- **Тема и предмет сравниваются точно**, но пробелы по краям обрезаются при записи и в фильтрах.
- Удаления задач нет: в критерии его нет, а запуски могли уже показать задачу ученику.

## Последствия

- Критерий «задачи создаются и выбираются по теме и сложности» закрыт тестом `test_tasks_are_created_and_chosen_by_topic_and_difficulty` в `tests/api/test_tasks_api.py`: он идёт на настоящем блоке из `blocks/`. Есть и ручная проверка `uv run python -m experiments.api_check`.
- Манифест блока живёт в `blocks/source/task_bank/block.yaml`. Копия в `docs/examples/manifests/` осталась, потому что по ней тесты контракта проверяют стыковку сценариев. Совпадение копий проверяет тест блока.
- В настройки блока добавлено необязательное поле `subject`: хранилище умеет искать и по предмету.
- Тесты блока лежат рядом с ним и импортируют только контракты. Это правило 1 в `.importlinter`: тест внутри пакета блока — тоже код блока. Проверка «встроенные блоки загружаются» осталась в `tests/core/test_registry.py`.
- Запись в банк из пайплайна (Получатель «банк задач», задача 22) — это новое действие хранилища, то есть изменение контракта отдельной задачей с ADR (ADR 0014).
