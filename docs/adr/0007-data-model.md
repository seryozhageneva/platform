# ADR 0007. Модель данных: что в базе с первого дня и как это хранится

- **Статус:** принято
- **Дата:** 12.10.2026

## Контекст

В `docs/vision.md`, раздел «Модель данных», перечислено тринадцать сущностей. Задача 03 должна была превратить их в таблицы PostgreSQL, миграции и репозитории. По дороге понадобилось решить шесть вещей, о которых документы молчали:

1. заводить таблицы для всех тринадцати сущностей сразу или только для части;
2. как хранить версии пайплайна, если запуск привязан к той версии, с которой стартовал;
3. как хранить состояние запуска, если его форма (`RunState`) в задаче 04 может уточниться;
4. чем обозначать записи, если в контракте все идентификаторы — строки;
5. как обеспечить правило «каждый преподаватель видит только своё»;
6. на какой базе идут тесты.

## Варианты

**Сколько таблиц.** Все тринадцать сущностей сразу или только те, форма которых уже определена. Все сразу — полная схема с первого дня, но шесть таблиц пришлось бы придумывать: их форма зависит от решений, которых ещё нет. Таблицу, созданную наугад, потом всё равно переделывают миграцией.

**Версии пайплайна.** Хранить в запуске копию графа или вести отдельную таблицу версий. Копия в каждом запуске — это тот же граф тридцать раз для тридцати учеников одного урока.

**Состояние запуска.** Отдельный столбец на каждое поле `RunState`; одно JSON-поле на всё; столбцы для того, по чему ищут, и JSON для остального.

**Ключ пайплайна.** Взять ключом поле `id` из файла пайплайна (`scenario_1_training`) или завести свой.

**База для тестов.** Подделка в памяти (SQLite), отдельный контейнер на каждый прогон или отдельная база в том же контейнере PostgreSQL.

## Решение

### Семь сущностей сейчас, шесть — позже

Сейчас создаются таблицы для семи сущностей, форма которых определена документами. Таблиц получается девять: у групп отдельно хранится состав, у пайплайнов — версии.

| Таблица | Что хранит |
| --- | --- |
| `users` | администраторы, преподаватели, ученики |
| `groups`, `group_members` | группы преподавателя и их состав |
| `tasks` | банк задач; поля совпадают с типом `Task` из контракта |
| `pipelines`, `pipeline_versions` | пайплайны и их версии |
| `assignments` | назначения: пайплайн с параметрами — ученику или группе |
| `runs` | запуски и их состояние |
| `events` | журнал событий |

Остальные добавляет миграцией задача, где таблица впервые нужна и где решается то, от чего зависит её форма:

| Сущность из записки | Задача | От чего зависит форма |
| --- | --- | --- |
| LLMCall — журнал вызовов модели | 07 | как слой моделей записывает вызовы, не подключая базу |
| Submission — работа ученика | 10 | где хранятся файлы работ |
| Approval — подтверждение | 18 | как устроена пауза на преподавателе |
| Connection — подключение | 23 | как шифруются ключи |
| Trigger — расписание | 26 | по ADR 0005 способы запуска записаны в самом пайплайне; в базе понадобится только то, что нужно планировщику |
| BlockRegistry — реестр блоков | 06 | открытый вопрос 26; блоки читаются из папок, таблица может не понадобиться вовсе |

### Версии пайплайна — отдельная таблица

`pipelines` хранит, чей пайплайн и какая версия последняя; `pipeline_versions` — сам граф. Каждое сохранение создаёт новую версию, старые не меняются. Запуск ссылается на пару «пайплайн, версия», и база не даст сослаться на версию, которой нет.

### Состояние запуска: столбцы и JSON

Статус, пайплайн, версия, ученик, преподаватель и текст ошибки — отдельные столбцы: по ним кабинет ищет запуски («кто где застрял»). Всё остальное состояние движка — значения портов, счётчики, текущие узлы, ожидание человека — лежит в одном JSON-поле `state`. Если в задаче 04 в `RunState` появится новое поле, оно попадёт в `state` само, без миграции.

Пайплайн, версия, ученик и преподаватель записываются один раз, при создании запуска. Повторное сохранение меняет только статус, ошибку и `state`.

### Ключи — UUID, имя пайплайна — не ключ

Ключ каждой записи — UUID, его создаёт программа. В контракте идентификаторы остаются строками: хранилище переводит строку в UUID на входе и обратно на выходе.

Поле `id` в файле пайплайна — читаемое имя, оно хранится в столбце `slug`. Ключом оно быть не может: два преподавателя могут загрузить один и тот же пример. Значит, `pipeline_id` в состоянии запуска — это ключ из базы, а не имя из файла.

### Владелец записи

У ученика, группы, задачи и пайплайна записан преподаватель-владелец (`owner_id`). Методы репозиториев, которыми пользуется кабинет, принимают владельца первым аргументом и ищут только в его записях: запроса «покажи всё» нет.

### Один вызов репозитория — одна транзакция

Репозиторий получает фабрику сессий и на каждый вызов открывает свою транзакцию. Это совпадает с интерфейсом `RunStore`, где каждый метод самостоятелен.

### Тесты — на отдельной базе в том же PostgreSQL

Тесты создают базу `platform_test`, применяют к ней миграции и после себя её удаляют. Рабочая база `platform` не затрагивается. Если PostgreSQL не запущен, тест падает с подсказкой, а не пропускается: пропущенный тест выглядел бы как зелёный. Тесты отказываются работать, если адрес базы указывает не на этот компьютер, — чтобы их нельзя было случайно запустить на сервере пилота.

Допустимые значения (роль, статус, способ проверки) проверяет сама база ограничениями `CHECK`, а не только код.

## Последствия

- Задача 04 получает готовое хранилище `PgRunStore`; ей остаётся движок и один тест «состояние в базе».
- Задачи 06, 07, 10, 18, 23, 26 становятся на одну миграцию больше. Это отмечено в карте.
- Движок и слой сборки должны давать запускам идентификаторы-UUID. В тестах движка с хранилищем «в памяти» годится любая строка, но в базу такая не сохранится — `PgRunStore` ответит понятной ошибкой.
- Значения портов хранятся как JSON. Движок кладёт в состояние то, что можно записать в JSON; даты при этом превращаются в строки.
- Новое значение в перечислении контракта (статус запуска, способ проверки) требует миграции: ограничение `CHECK` в базе само не обновится. Это ловят тесты, которые сохраняют каждое значение перечисления.
- Тест `test_tables_and_migrations_agree` падает, если в коде появилась или изменилась таблица, столбец или индекс, а миграцию не написали. Изменения ограничений `CHECK` и значений по умолчанию он не видит: их ловят тесты, которые сохраняют каждое значение перечисления.
- Не всякий текст можно записать в JSON-поле PostgreSQL: строка с нулевым символом даёт ошибку базы, а «не число» и бесконечность превращаются в пустое значение. Нулевой символ встречается в тексте, извлечённом из PDF; кто чистит такие значения, решается в задаче 19.
- Столбец `runs.assignment_id` хранилище запусков не заполняет: в `RunState` такого поля нет. Связь запуска с назначением понадобится триггеру «ученик» (задача 14) — отдельным методом репозитория либо изменением контракта с ADR.
- У групп и назначений пока есть только таблицы; репозитории появятся в задачах 13 и 14.
- Два одновременных прогона тестов на одном компьютере мешают друг другу: база `platform_test` у них общая.
- Одна транзакция на вызов означает, что два репозитория нельзя объединить в одно «всё или ничего». Пока это не нужно; если понадобится в API — отдельным решением.
- Удалить пайплайн, у которого есть запуски, база не даст. Как преподаватель «удаляет» пайплайн (скорее всего — прячет), решается в задаче 16.
- В столбцах входа лежат только хэши пароля и личной ссылки. Как ссылка выдаётся и отзывается — открытый вопрос 14, задача 13.
