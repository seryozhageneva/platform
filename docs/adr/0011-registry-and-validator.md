# ADR 0011. Реестр блоков и валидатор пайплайнов

- **Статус:** принято
- **Дата:** 13.10.2026

Контракт не меняет: всё, что понадобилось, в `backend/core/contracts/` уже было (ADR 0004, 0005).

## Контекст

Движок (ADR 0008, 0010) выполняет пайплайн, но таблицу блоков ему составляют тесты, а плохой пайплайн он не отличает от хорошего: цикл без ограничителя будет крутить бесконечно. Задача 06 добавляет две части ядра:

- **реестр** — находит установленные блоки и отдаёт движку таблицу блоков;
- **валидатор** — проверяет пайплайн до сохранения и до запуска.

Документы оставили на эту задачу пять вопросов:

1. нужна ли реестру таблица в базе (ADR 0007);
2. что делать, если один из блоков сломан;
3. что будет с сохранённым пайплайном, когда блок обновится (открытый вопрос 26);
4. блок с последствиями без Подтверждения — ошибка или предупреждение (открытый вопрос 25);
5. что значит «в каждом цикле есть ограничитель», если у ограничителя есть обнуление счётчика и переход «попытки кончились».

## Варианты

**Где живёт реестр.** (а) Таблица в базе, куда блоки записываются при установке. (б) Папки: реестр читает их при старте.

**Сломанный блок.** (а) Платформа не стартует. (б) Блок не загружается, остальные работают.

**Версия блока.** (а) Узел пайплайна хранит версию блока, на сервере стоят несколько версий. (б) Узел ссылается на блок по имени, установлена одна версия.

**Без Подтверждения.** (а) Ошибка: пайплайн не сохраняется. (б) Предупреждение: сохраняется, редактор показывает.

**Ограничитель в цикле.** (а) В круге есть хотя бы один узел с ограничителем. (б) Проверяется, что круг действительно кончится.

## Решение

### Реестр читает папки, таблицы в базе нет

Блок — папка с манифестом `block.yaml` (вариант б). `load_registry(папка)` обходит папку и возвращает три вещи:

| Что | Кому |
| --- | --- |
| `manifests` — манифесты всех исправных блоков | валидатору и редактору |
| `blocks` — таблица блоков `LoadedBlock` | движку |
| `problems` — почему блок не загружен: файл и причина | администратору |

Таблица в базе повторяла бы содержимое папок и могла бы с ним разойтись. Этим закрыт пункт «BlockRegistry» из ADR 0007: миграции в задаче 06 нет.

Функцию встроенного блока реестр находит по строке `entrypoint` из манифеста и подключает по имени (`importlib`). Обычным импортом ядро блоки не подключает (ADR 0003).

### Что реестр проверяет

- манифест соответствует контракту;
- имя блока не занято другим блоком;
- `entrypoint` указывает на код в папке этого же блока: манифест не может назвать блоком чужую функцию, например `os:system`, функцию соседнего блока или блока, вложенного в его папку;
- модуль загрузился, функция в нём есть и объявлена как `async def`;
- среди инструментов агента (`tools`) нет инструмента с последствиями;
- данные с одним названием-уточнением описаны одинаково. Порты стыкуются по названию уточнения, а не по содержимому, и следить за совпадением названий ADR 0004 поручил реестру. Сравниваются только порты, у которых описание (`schema`) есть.

**Сломанный блок не загружается и остальным не мешает** (вариант б). Один плохой сторонний блок не должен останавливать уроки на остальных. Это верно для любой поломки: файл не читается или сохранён не в UTF-8, код блока падает при загрузке или пытается завершить программу, способ вызова не смог подключить блок.

### Блоки `mcp` и `http`

Ядро в сеть не ходит (ADR 0006). Поэтому вызывать такие блоки реестр учится у слоя сборки: тот передаёт **способ вызова** — функцию, которая по манифесту даёт `run`. Пока способа нет (MCP-клиент — задача 23, песочница — задача 21), манифест блока в реестре есть, а в таблице для движка блока нет. Валидатор и редактор такой блок видят.

### Версия блока: одна установленная, ссылка по имени

Вариант (б). Узел по-прежнему ссылается на блок только по имени, формат пайплайна не меняется.

- Пайплайн проверяется по текущим манифестам при сохранении и перед запуском (подключение — задачи 08 и 16).
- Блок обновился и изменил порты — валидатор назовёт узел и причину, преподаватель правит пайплайн.
- Запуск, который уже шёл, остановится с ошибкой на этом узле: движок сверяет входы и результат блока с манифестом (ADR 0008).

Несколько версий одного блока рядом — это изменение формата пайплайна и хранения; для ВКР не нужно.

### Валидатор: ошибки и предупреждения

`validate(пайплайн, манифесты)` возвращает отчёт: список ошибок и список предупреждений. С ошибкой пайплайн не сохраняется, с предупреждением — сохраняется.

Сначала вызывается проверка стыковки из контракта (`check_wiring`), её находки — ошибки. Дальше валидатор добавляет свои:

| Код | Что не так | Уровень |
| --- | --- | --- |
| `unreachable` | до узла нельзя дойти от старта | ошибка |
| `unbounded_loop` | круг может повторяться без конца | ошибка |
| `never_written` | обязательный вход, развилка или «для каждого» читает узел, который раньше не выполняется | ошибка |
| `bad_config` | настройки узла не подходят под схему `config` блока | ошибка |
| `tool_with_side_effects` | агенту разрешён инструмент с последствиями | ошибка |
| `no_approval` | до блока с последствиями можно дойти, минуя Подтверждение | предупреждение |

Тело «для каждого» проверяется как отдельный маленький граф, который начинается с узла `start`.

### Без Подтверждения — предупреждение

Вариант (б), решение автора. В сценарии 1 итог урока уходит ученику в Telegram без Подтверждения: это его собственный результат, и ждать преподавателя после каждого урока незачем. Валидатор не может отличить такой случай от рассылки оценок всей группе, поэтому не запрещает, а предупреждает.

«Перед блоком есть Подтверждение» значит: на любом пути от старта к блоку Подтверждение выполняется. Для узла в теле «для каждого» засчитывается и Подтверждение перед самим «для каждого» — так устроены сценарии 2 и 4.

Если у Подтверждения стоит ограничитель с переходом «попытки кончились», этот переход идёт мимо Подтверждения: он срабатывает как раз тогда, когда Подтверждение уже не выполняется. Пример: «отклонил — переделай» не больше двух раз, а потом — отправить. Блок на таком пути предупреждение получает.

### Когда круг считается ограниченным

Вариант (б). Правила «в круге есть узел с ограничителем» мало: счётчик может обнуляться на узле того же круга, и тогда предела он не достигнет никогда.

Валидатор ищет узлы, которые за запуск выполняются **конечное число раз**:

1. узел, который не стоит ни в одном круге;
2. узел с ограничителем, счётчик которого не обнуляется;
3. узел с ограничителем, счётчик которого обнуляется на узле из уже найденных;
4. узел с ограничителем, счётчик которого обнуляется на узле, откуда к нему нельзя вернуться: такое обнуление уже ничему не мешает.

Из найденных узлов убираются обычные переходы — рано или поздно они перестанут срабатывать; переход «попытки кончились» остаётся. Шаги повторяются, пока находится что-то новое. Если после этого в графе остался круг — он бесконечный, и это ошибка.

Так ловятся три разных случая:

- в круге нет ни одного ограничителя;
- ограничитель обнуляется внутри своего же круга (или два ограничителя обнуляют друг друга);
- круг из одних переходов «попытки кончились»: узлы отправляют запуск друг к другу, и ни один уже не выполняется.

Внутри тела «для каждого» счётчик, который обнуляется на узле снаружи, считается необнуляемым: пока идёт один элемент, внешний узел не выполняется.

**Переход «попытки кончились», который не может сработать, не считается вовсе** — ни при поиске кругов, ни при проверке достижимости. Он срабатывает, только если в узел можно вернуться, не выполнив по дороге узел, который обнуляет его счётчик. Узел, в который ведёт только такой переход, — недостижимый, и в ошибке это сказано.

Проверка сверена с настоящим шагом движка на десятках тысяч случайных графов: пайплайна, который движок крутил бы бесконечно, а валидатор пропустил, не нашлось.

### Настройки и параметры

Настройки узла сверяются со схемой `config` из манифеста. Значение параметра пайплайна известно только при назначении, поэтому на месте ссылки `{"$param": "имя"}` сверяется тип параметра с типом настройки. Целый параметр годится и там, где ждут число. Проверки, которым нужно само значение («элементы списка не повторяются», «подходит один из вариантов»), для настройки с параметром внутри пропускаются.

Схему настроек пишет автор блока. Если она сама неисправна — например, ссылается на описание, которого нет, — валидатор не падает, а сообщает об этом ошибкой `bad_config`.

Сообщения — по-русски: какая настройка и что с ней не так.

## Последствия

- Критерий «5 сломанных пайплайнов отклоняются с понятной ошибкой» закрыт тестом `test_broken_pipeline_is_rejected` в `tests/core/test_validator.py`: десять сломанных сценариев, у каждого сверяются узел, код и текст.
- Проверка кругов перестраховывается в одном редком случае: она не считает, сколько именно раз можно вернуться в узел. Переход «попытки кончились», ведущий в сам же узел, она отклонит, даже если вернуться в узел можно лишь однажды и попытки на деле не кончатся. Такой переход — ошибка автора пайплайна в любом случае: сработав, он зациклил бы запуск.
- Открытые вопросы 25 и 26 закрыты.
- Валидатор пока никто не вызывает: сохранение и запуск появятся в задачах 08 и 16. До тех пор движок по-прежнему выполнит любой пайплайн, который ему передали.
- Тест `test_builtin_blocks_load_without_problems` загружает настоящую папку `blocks/`. Сейчас блоков в ней нет; каждый новый блок (с задачи 09) обязан проходить этот тест.
- Инструмент считается «с последствиями», если им пользуется блок с `side_effects: true`. Пометки самого MCP-сервера (`ToolInfo.read_only`) сверяются, когда появится MCP-клиент, — задачи 23 и 29.
- `never_written` ловит только случай «ни на одном пути». Если данные могут не успеть появиться на одном из путей, валидатор молчит, а движок остановит запуск с ошибкой «обязательный вход без данных». Строгая проверка давала бы ложные ошибки на привязках с несколькими ссылками.
- Валидатор не смотрит, по какому исходу вышли из Подтверждения: блок, поставленный на ветку «отклонено», предупреждения не получит.
- Лишняя настройка, которой нет в схеме блока, — ошибка только если схема сама это запрещает (`additionalProperties: false`). Опечатку в названии необязательной настройки валидатор не заметит.
- Значения параметров при запуске («тема заполнена, число задач — число») валидатор не проверяет: это задача 08, где значения появляются.
- Папка с блоками должна лежать в путях поиска Python. Для встроенных блоков это так; установка сторонних блоков из другой папки — задача 33.
- Загрузка блока выполняет его код. Сторонний блок по-прежнему работает в одном процессе с ядром — открытый вопрос 16.
- Реестр читает папки один раз, при вызове. Новый блок появится после перезапуска сервера.
