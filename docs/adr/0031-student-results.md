# ADR 0031. Результаты учеников через хранилище платформы

- **Статус:** принято
- **Дата:** 11.11.2026

Меняет контракт: в интерфейсе `PlatformStore` (`backend/core/contracts/interfaces.py`) новое
действие чтения `find_results` и две модели — `StudentResults` и `WorkResult`. Дополняет
ADR 0014, ADR 0016 и ADR 0026.

## Контекст

В задаче 25 появляется сценарий 4: раз в неделю платформа сама составляет для преподавателя
сводку — кто отстаёт, какие ошибки типичны, что повторить. Первый шаг сценария — «собрать
результаты учеников из хранилища платформы» (блок `source.platform_results` в
`docs/examples/pipelines/scenario-4-analytics.json`).

Хранилище платформы умеет читать задачи банка и файлы и записывать результаты (ADR 0014,
0023, 0026), но не умеет отвечать на вопрос «как учились мои ученики». ADR 0014 прямо
говорит, что каждое новое действие, в том числе «результаты группы (задача 25)», — изменение
контракта отдельной задачей с ADR. Это задача 24b.

По ходу нашлись два пробела в данных:

1. Вердикт проверки по эталону (`check.exact`, сценарий 1) рядом с работой ученика не
   записывался: слой сборки записывал только вердикты проверки по рубрике и тестами кода
   (ADR 0016, 0025). Работы из тренировки оставались «непроверенными».
2. В таблице работ нет поля «верно или нет»: есть балл, но у проверки по рубрике он бывает
   частичным, и угадывать «верно» по баллу ненадёжно.

## Варианты

**Чьи результаты.**

- (а) Всех учеников преподавателя. Группы в базе есть (ADR 0007), но создать группу на
  платформе пока нельзя: нет ни запроса, ни экрана.
- (б) Учеников одной группы. Сначала пришлось бы сделать управление группами — ещё
  полдня–день работы.

**Что отдавать о работе.**

- (а) Только итог: задача, тема, откуда работа, когда сдана, проверена ли, верно ли, балл.
- (б) Ещё и текст ответа и комментарий проверки. Сводке они почти не нужны, а текст ответа —
  это то, что ученик написал сам, и он уходил бы в модель целиком.

**Откуда подсказки.** Подсказки ИИ-тьютора не хранятся отдельно: тьютор пишет в журнал
событие `hint_checked` с отметкой, одобрил ли подсказку контролёр (ADR 0018).

- (а) Считать одобренные события `hint_checked` в запусках учеников.
- (б) Завести таблицу подсказок. Ещё одна таблица ради одного числа.

## Решение

Вариант (а) во всех трёх вопросах (по первому — решение автора). Действие:

| Действие | Что делает |
| --- | --- |
| `find_results(since=…)` | результаты всех учеников преподавателя с момента `since`, по алфавиту |

Для каждого ученика — `StudentResults`: номер, имя, список работ `WorkResult` от старых к новым
и число полученных подсказок. В `WorkResult`: номер задачи, тема (если задача из банка), откуда
работа (`platform` или `moodle`), когда сдана, статус проверки (`unchecked`, `preliminary` —
оценил ИИ, `confirmed` — окончательно), верно ли, балл и максимум.

Правила:

- **Только свои ученики.** Хранилище уже ограничено преподавателем запуска (ADR 0014): чужих
  учеников, их работ и подсказок блок не видит.
- **Ученик без работ тоже в списке.** Для сводки «ничего не решал» — тоже результат.
- **Пробный запуск преподавателя не считается.** У ручного запуска нет ученика: его работы и
  подсказки никому не засчитываются.
- **Без текста ответа и комментария.** Только итог проверки.
- **Имя ученика отдаётся.** Без него сводка не скажет, кто отстаёт. Скрыть имя от модели можно
  настройкой `data_fields` блока ИИ-обработки (ADR 0029).
- **Время с часовым поясом.** `since` без пояса — `ValueError`: иначе «с пятницы 18:00»
  означало бы разное время на сервере и у преподавателя.
- **Подсказка засчитывается, если её одобрил контролёр**: только такую ученик увидел.
- **Вердикт записывается и у проверки по эталону.** Слой сборки записывает вердикт `check.exact`
  рядом с работой так же, как вердикты рубрики и тестов кода.
- **В таблице работ новый столбец `correct`** — поле `correct` вердикта. Миграция `0009`. У
  старых работ он пуст.
- **Подделка** `FakeStore` принимает готовые результаты в `results`, отбрасывает работы раньше
  `since` и отдаёт число подсказок как есть: журнала у неё нет. Ученики из `results` считаются
  учениками преподавателя — им можно адресовать результат.

## Последствия

- Движок не меняется. Блок, который отдаёт результаты в пайплайн, — `source.platform_results` —
  делается в задаче 25.
- В примере сценария 4 параметр `group_id` станет не нужен; пример правится в задаче 25.
- Если понадобятся группы, к `find_results` добавляется необязательный фильтр по группе;
  остальное в договоре не меняется.
- Работы из Moodle попадают в результаты, только если они записаны в таблицу работ и у них есть
  ученик платформы. Сейчас работы из Moodle туда не записываются (ADR 0028), так что оценки из
  Moodle сводка будет брать отдельным источником (задачи 27–28).
- Схемы в `docs/schemas/` не меняются: интерфейсы служб в них не входят.
