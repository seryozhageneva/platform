# ADR 0034. Запуск по событию Moodle и оценки в Moodle

- **Статус:** принято
- **Дата:** 12.11.2026

Дополняет ADR 0028 (MCP-сервер Moodle), ADR 0032 (запуск по расписанию) и ADR 0033 (правило
повторов MCP-действий). Модели в `backend/core/contracts/` не меняются: способ запуска
`moodle_event` с настройкой `poll_minutes` уже был в формате графа, а номера сдач едут в
существующем поле `payload` события.

## Контекст

Задача 27: сдача работы в Moodle должна запускать сценарий 2, а оценка — появляться в
Moodle. До неё сценарий 2 запускался только вручную, каждый запуск брал все сданные работы
задания, а последний цикл «оценка в Moodle и письмо студенту» был отрезан.

## Решение

**Опрос, а не вебхук** (решение 7 в `docs/vision.md`). Тот же рабочий процесс arq, что
проверяет расписания, раз в минуту (на 30-й секунде) смотрит включённые наблюдения. Если
с прошлого опроса прошло `poll_minutes` (по умолчанию 5, от 1 до 1440), он вызывает новый
инструмент `moodle.list_submissions`. Тот отдаёт номера сданных работ, номера студентов и
время сдачи — без файлов, поэтому опрос лёгкий.

**Наблюдение — таблица `moodle_watches`, миграция 0012.** Как у расписания: после
сохранения графа преподаватель включает запуск по событию в редакторе и задаёт параметры
пайплайна. API — `GET` и `PUT /api/v1/pipelines/{id}/moodle-watch`. Таблица хранит время
последнего опроса и текст последней ошибки опроса — его видит преподаватель в редакторе.
Если из графа убрать способ запуска `moodle_event`, наблюдение выключается в той же
транзакции. Курс и задание опрос берёт из настроек блока «Источник: работы из Moodle» в
графе, поэтому проверка запуска по событию требует ровно один такой блок вне «для каждого»
и вход `event`, привязанный к триггеру.

**Только новые работы — таблица `moodle_seen_submissions`.** Ключ — пайплайн, номер сдачи и
время сдачи. Пересданная после доработки работа получает новое время и считается новой.
На все новые сдачи одного опроса создаётся один запуск: так преподаватель видит одну таблицу.
Номера сдач записываются в `payload` события, и блок «Источник» передаёт их инструменту
`get_submissions` (`submission_ids`): скачиваются только эти файлы. Ручной запуск и запуск по
расписанию по-прежнему берут все сданные работы.

**Сдача отмечается обработанной вместе с запуском.** Отметка, запуск и запись в журнал
пишутся одной транзакцией, которая откатывается, если Redis не принял задание: тогда
следующий опрос возьмёт эти сдачи снова. Упавший потом запуск сам не повторяется —
преподаватель продолжает его с упавшего узла (ADR 0008). Два рабочих процесса не создадут
двух запусков: опрос сначала «занимает» строку наблюдения, а повторная отметка той же сдачи
откатывает вторую транзакцию.

**Когда наблюдение включено впервые,** уже сданные работы тоже считаются новыми и попадают в
первый запуск. Подтверждение перед оценкой не даёт им уйти в Moodle без преподавателя.

**Оценка — инструмент `moodle.save_grade` и блок `sink.moodle_grades`.** Инструмент помечен как
действие с последствиями: агенту он недоступен, а валидатор предупреждает, если перед блоком
нет Подтверждения (ADR 0011). Чья работа и по какому заданию — платформа берёт из `meta` файла
(`moodle_course_id`, `moodle_assignment_id`, `moodle_user_id`), а не из ответа модели.
Баллы вердикта пересчитываются в шкалу задания Moodle: `score / max_score × максимальная оценка`,
с округлением до сотых. Вердикт без баллов даёт полный балл или ноль. Задание, которое
оценивается шкалой или без оценки, — понятная ошибка. Комментарий уходит простым текстом
(`FORMAT_PLAIN`): Moodle не исполнит разметку из текста модели. Повтора MCP-действия нет, как в
ADR 0033; повторная ручная отправка ставит ту же оценку.

**Письмо студенту Moodle из сценария 2 убрано** (решение автора). У студента Moodle нет
карточки на платформе (ADR 0028), и `sink.email` не знает, куда писать. О новой оценке
студенту сообщает сам Moodle.

**Права в тестовом Moodle.** `experiments/moodle_seed.php` добавляет в сервис `platform`
функции `mod_assign_save_grade`, `mod_assign_get_grades` и `mod_assign_get_submission_status`
(две последние — для проверки) и включает у задания комментарий к оценке. Это работает и на
Moodle, наполненном до задачи 27. Пользователь платформы по-прежнему называется
`platform_reader`, хотя теперь ставит оценки: переименование сломало бы выданный токен.

## Проверка

- `tests/triggers/test_moodle_event.py`: один запуск на новые сдачи, повтора нет, пересданная
  работа — новая, два рабочих процесса — один запуск, сбой Redis не теряет сдачи, ошибка
  Moodle видна преподавателю, выключение при правке графа.
- `tests/e2e/test_scenario_2_grading.py`: пример `scenario-2-grading.json` без изменений —
  включение через API → опрос → запуск → таблица → оценки в Moodle. Первый тест — на
  подделке Moodle, второй — на тестовом Moodle, где оценка и комментарий читаются обратно
  из Moodle.

## Последствия

- Число запусков Moodle ограничено частотой опроса: при `poll_minutes: 5` работа ждёт до
  пяти минут.
- Каждый опрос — запуск дочерней программы MCP-сервера (около секунды). Для десятков
  наблюдений это допустимо; для сотен понадобится постоянный сервер.
- Если студент пересдал работу, пока первый запуск ждёт Подтверждения, второй опрос создаст
  второй запуск с новой версией. Подтверди преподаватель сначала новый, потом старый, в
  Moodle останется оценка за старую версию. Обе таблицы у преподавателя перед глазами, поэтому
  в коде это не запрещается.
- Групповые сдачи Moodle (номер студента 0) не поддерживаются — открытый вопрос 32.
- Из-за опроса и оценки токен Moodle преподавателя должен давать права и на чтение, и на
  выставление оценок.
