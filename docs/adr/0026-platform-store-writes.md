# ADR 0026. Запись результатов через хранилище платформы

- **Статус:** принято
- **Дата:** 11.11.2026

Меняет контракт: в интерфейсе `PlatformStore` (`backend/core/contracts/interfaces.py`) три новых действия — первые действия записи. Дополняет ADR 0014 и ADR 0023.

## Контекст

В задаче 22 появляются блоки-получатели: «Кабинет», «Хранилище» и «Файл». Они стоят в конце пайплайна и сохраняют то, что пайплайн сделал: задачи — в банк преподавателя, готовые PDF или DOCX — в файлы платформы, итоги — в кабинет преподавателя или ученика.

До этой задачи хранилище платформы только читало (ADR 0014, ADR 0023). Работы учеников записывает слой сборки, а не блок (ADR 0016), но там запись следует из паузы движка. Что и куда сохраняет получатель, решает сам блок по своим настройкам, поэтому без действий записи ему не обойтись.

Есть ещё одна трудность. Движок повторяет упавший блок до трёх раз (ADR 0008), а рабочий процесс может оборваться после записи, но до сохранения состояния запуска (ADR 0022). Если блок сохранит задачу и упадёт, повтор создаст вторую такую же задачу.

## Варианты

**Как блок записывает.**

- (а) Новые действия в `context.store`. Хранилище уже ограничено преподавателем запуска, подделка для тестов уже есть — так же решено для файлов в ADR 0023.
- (б) Блок возвращает «что сохранить» в выходе, а записывает слой сборки. Блок проще, но слою сборки пришлось бы понимать выходы каждого получателя, а это знание о блоках вне блоков (правило 4).
- (в) Отдельная служба `context.sink`. Ещё одно поле в `context` и ещё одна подделка ради трёх действий.

**Как не записать дважды при повторе.**

- (а) Блок передаёт ключ результата. Номер записи вычисляется из преподавателя, запуска, узла, вида записи и ключа, а вставка при совпадении номера ничего не делает и возвращает уже сохранённую запись.
- (б) Отдельная таблица «что уже записано». Ещё одна таблица и ещё одна транзакция ради того же.
- (в) Ничего не делать. Дубликаты в банке задач преподаватель заметит не сразу.

## Решение

Вариант (а) в обоих вопросах. В `PlatformStore` три действия:

| Действие | Что делает |
| --- | --- |
| `save_task(task, key=…)` | сохраняет задачу в банк преподавателя как подтверждённую и возвращает её с номером из банка |
| `save_file(key=…, name=…, kind=…, media_type=…, content=…)` | сохраняет готовый файл преподавателя и возвращает ссылку `File` |
| `publish_result(key=…, title=…, content=…, student_id=None)` | записывает результат в кабинет преподавателя или его ученика и возвращает номер записи |

Правила:

- **Запись привязана к запуску и узлу.** Хранилище создаёт обёртка блока в сборке, и номер запуска и узла она берёт из `context`. Блок их не передаёт и подменить не может.
- **Ключ выбирает блок.** Он должен быть устойчивым: при повторе тот же блок с теми же входами передаёт тот же ключ. В пределах одного запуска и узла одинаковый ключ — одна запись. Повтор с тем же ключом возвращает первую запись, даже если содержимое изменилось.
- **Номер записи вычисляется, а не выдаётся.** `uuid5` от преподавателя, запуска, узла, таблицы и ключа; вставка `ON CONFLICT DO NOTHING`. Две одновременные записи с одним ключом дают одну строку.
- **Задача из блока сразу подтверждена.** Подтверждение преподавателем делает узел подтверждения перед получателем (ADR 0021). Черновик в банк из пайплайна не попадает.
- **Результат адресуется только своему ученику.** Чужой, неизвестный или «странный» номер ученика, а также номер преподавателя вместо ученика — ошибка `ValueError`, запись не делается. Без ученика результат адресован преподавателю.
- **Ошибка базы не показывает данные.** Текст ошибки PostgreSQL может содержать условие задачи, результат или байты файла, а журнал запуска видит преподаватель. Поэтому хранилище заменяет её на `RuntimeError` с одним названием вида ошибки.
- **Результаты кабинета лежат в новой таблице `cabinet_results`:** владелец, запуск, узел, ученик (если есть), заголовок и содержимое в JSON. Миграция `0007`.
- **Подделка** `FakeStore` записывает так же: сохранённая задача и файл сразу видны через чтение, результаты собираются в списке `published`, повтор ключа не создаёт вторую запись. Учеников, которым можно адресовать результат, тест передаёт в `students`.

## Последствия

- Движок не меняется. Меняется обёртка блока в сборке: хранилище теперь создаётся на запуск и узел.
- Сетевые блоки (`mcp`, `http`) по-прежнему хранилища не получают (ADR 0014). Выгрузка во внешние системы — через MCP-адаптеры (задача 23).
- Показ результатов в кабинете — API и экран — делается в задаче 22 вместе с блоками-получателями. В этой задаче только запись и таблица.
- `save_file` не проверяет тип, размер и имя файла, в отличие от загрузки через API (ADR 0023): что блоку можно сохранять, решает сам блок-получатель «Файл». Ограничения для файлов, которые отдаются на скачивание, вводятся в задаче 22 вместе с этим блоком.
- Одна подделка `FakeStore` соответствует хранилищу одного узла: тест, где два узла делят одну подделку, должен давать им разные ключи.
- Если блок поменяет способ построения ключа, повтор старого запуска создаст новую запись. Ключ стоит строить из входов, а не из времени или случайного числа.
- Схемы в `docs/schemas/` не меняются: `RunContext` и интерфейсы служб в них не входят.
