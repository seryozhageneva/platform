# ADR 0009. Состояние запуска помнит порядок записи выходов

- **Статус:** принято
- **Дата:** 12.10.2026

Меняет контракт: модель `RunState` в `backend/core/contracts/state.py`. Закрывает открытый вопрос 27.

## Контекст

Вход блока можно привязать к нескольким выходам сразу — «ссылки на выбор» (ADR 0005). Тогда берётся значение, записанное последним. В сценарии 1 так устроен ответ ученика: он приходит либо из формы, либо после распознавания фото.

Состояние запуска хранило только сами значения: «узел → порт → значение». Какое из двух значений свежее, по нему понять нельзя. Положиться на порядок, в котором значения лежат в состоянии, тоже нельзя: в базе состояние хранится в JSON-поле (ADR 0007), а PostgreSQL порядок ключей в нём не сохраняет. Кроме того, повторная запись старого выхода его место среди ключей не меняет.

Движку v1 это было не нужно — в прямой цепочке у входа одна ссылка (ADR 0008). Движок v2 (задача 05) без этого не может выполнить сценарии 1 и 2: в них есть ссылки на выбор.

Заодно пришлось решить второй вопрос к состоянию. Узел «для каждого» перебирает список; если запуск встал на паузу или сервер перезапустился посреди списка, движок должен знать, на каком элементе он остановился. В состоянии этого не было.

## Варианты

**Как запомнить порядок.**

- (а) Счётчик шагов в состоянии и номер шага у каждого записанного выхода. Два новых поля; номера сами по себе никому не нужны — нужен только ответ «что свежее».
- (б) Хранить значение вместе с номером шага: «узел → порт → {значение, шаг}». Меняет уже существующее поле `ports` и всё, что его читает.
- (в) Список выходов в порядке записи. Одно новое поле; список в JSON порядок сохраняет.

**Где держать номер текущего элемента «для каждого».**

- (а) В счётчиках ограничителей (`counters`). Но у узла «для каждого» может быть и свой ограничитель — два числа с одним именем.
- (б) Среди значений выходов узла. Но выходы читаются привязками, служебному числу там не место.
- (в) Отдельное поле.

## Решение

В `RunState` два новых поля.

| Поле | Что хранит |
| --- | --- |
| `write_order` | выходы «узел.порт» в порядке записи, от самого старого к самому свежему (вариант в) |
| `item_index` | для узла «для каждого» — номер элемента, на котором он стоит, с нуля (вариант в) |

И два метода, чтобы порядок вёлся в одном месте, а не в каждом, кто пишет выходы:

- `write(узел, выходы)` — записывает выходы узла; каждый записанный выход переносится в конец списка, то есть становится самым свежим;
- `latest(ссылки)` — какая из ссылок записана последней; если ни одна не записана — ничего. У ссылки на поле записи (`узел.порт.поле`) смотрится сам выход `узел.порт`.

Состояние проверяет само себя: выход не может стоять в списке дважды, и в списке не может быть выхода, которого нет среди значений.

Движок v1 записывает выходы через `write` и при отмене шага (ADR 0008) возвращает прежний порядок. Выбирать «последнюю записанную» ссылку он начнёт в задаче 05 — тогда же начнёт заполняться `item_index`.

## Последствия

- Миграция базы не нужна: новые поля попадают в JSON-поле `state` сами (ADR 0007). Схемы в `docs/schemas/` не меняются: состояние запуска в них не входит.
- Запуск, сохранённый до этого изменения, читается: выход, которого нет в списке, считается самым старым. Таких запусков на сегодня нет, но правило записано в коде и проверено тестом.
- Порядок говорит только, что записано позже. Из какого прохода цикла значение — он не говорит: в цикле на порту может лежать значение от прошлой задачи. Для этого у `Answer`, `Verdict` и `Hint` по-прежнему есть `task_id` (`docs/contract.md`, «Соглашения о данных»).
- Тот, кто меняет `ports` напрямую, мимо `write`, обязан сам поправить `write_order`. В задаче 05 это понадобится один раз: перед каждым элементом «для каждого» значения узлов тела нужно убрать, иначе в собранное попадёт значение от прошлого элемента.
- `item_index` добавлен до того, как появился код, который его заполняет. Это сделано, чтобы задача 05 не останавливалась ради второго изменения контракта. Если в задаче 05 окажется, что нужна другая форма, поле меняется там же, новой ADR.
- Список растёт не длиннее числа выходов в пайплайне: повторная запись выхода не добавляет строку, а переносит её.
