# ВКР: платформа для построения персонализированных учебных пайплайнов на основе ИИ-агентов — рабочая записка

Oct 9, 2026 · @seryozhageneva

## Тема и суть

**Тема (согласована с научруком):** «Платформа для построения персонализированных учебных пайплайнов на основе ИИ-агентов».

**Суть.** Преподаватель в визуальном редакторе собирает учебный процесс из блоков: откуда взять данные, что с ними сделать, кому и куда отдать результат, когда всё это запускать. Внутри блоков работают ИИ-агенты, которые ведут каждого ученика в его темпе. Блоки — плагины с единым контрактом, любой может написать свой и поделиться им, как расширением в VS Code или Obsidian.

**Для кого:** преподаватели школы, репетиторы и преподаватели вуза. Один и тот же набор блоков покрывает подготовку к ЕГЭ в частной школе и работу с группой студентов в Moodle.

**Что изменилось после обсуждения с научным руководителем:**

- Блоки не придумываются заранее, а **выводятся из сценариев**: сценарий → шаги → похожие шаги объединяются в абстракцию → абстракция становится блоком. Например, «список почт студентов», «текст лекции» и «работа студента» — это один блок «Источник данных», настроенный на разные источники.
- Для подключения агентов к инструментам и внешним системам используем **MCP** там, где это возможно (модели обучены с ним работать), для простых случаев — HTTP.
- **Эксперимент необязателен** для бакалавриата: делаем инженерную оценку и мини-пилот как демонстрацию внедрения.
- Добавлен блок **«Триггер»**: пайплайн запускает не только ученик, но и преподаватель, расписание или событие.

## Обоснование: две статьи

Обе статьи показывают одно: ИИ-тьютор сильно помогает, но только если его поведение жёстко задано методикой, а не оставлено на усмотрение модели.

**Kestin, Miller и др., Гарвард, Scientific Reports, 2025.** Рандомизированный эксперимент на 194 студентах курса физики. ИИ-тьютор против активного обучения в аудитории. Прирост знаний с ИИ более чем вдвое выше, медианное время 49 минут против 60. Ключевые выводы для нас:

- системного промпта не хватило, чтобы вести студента по многошаговой задаче; шаги пришлось навязывать на уровне платформы;
- точность обеспечивали заранее написанные пошаговые решения, а не знания модели;
- подготовка промптов к одному уроку заняла несколько дней, разработка платформы — несколько месяцев.

**Bastani и др., Пенсильвания, PNAS, 2025.** Почти 1000 школьников, математика 9–11 классов, три группы: обычный чат GPT-4, GPT Tutor с ограничениями, без ИИ. На практике рост на 48% и 127% соответственно. Когда ИИ убрали, группа с обычным чатом написала контрольную на 17% хуже группы без ИИ; ограничения GPT Tutor эту потерю сняли. Ограничение главное — подсказки вместо готового ответа.

**Что из этого следует для проекта:**

1. Структуру урока задаёт система (граф блоков), а не промпт.
2. Ограничения тьютора обязательны и должны быть проверяемыми.
3. Эталонные решения — отдельная сущность, которую преподаватель вводит или подтверждает.
4. Подготовка урока дорогая, значит, нужен инструмент, который её удешевляет. Это и есть наша платформа.

## Научная новизна и практическая значимость

Новизна — в методе построения набора блоков из сценариев и в переносе методических ограничений ИИ из промпта в архитектуру.

**Научная новизна (формулировки для записки):**

1. Предложен метод выделения типовых блоков учебного процесса через декомпозицию сценариев на шаги и обобщение шагов в абстракции (источник, обработка, взаимодействие, проверка, получатель, триггер, подтверждение).
2. Предложена модель учебного пайплайна как графа блоков с условиями и циклами, в которой методические ограничения ИИ-агентов задаются структурно, а не только промптом.
3. Разработан контракт блока с двумя способами подключения: MCP для агентных инструментов и HTTP для простых сервисов, — обеспечивающий расширяемость платформы сторонними разработчиками.
4. Предложен механизм контроля утечки ответа: отдельный агент проверяет подсказки тьютора на раскрытие эталонного решения.

**Практическая значимость.** Платформа внедряется в частную школу и онлайн-практику автора; сценарии с Moodle применимы в вузе. Преподаватель автоматизирует проверку, подготовку материалов и обратную связь без программирования.

**Почему это программная инженерия.** Основной результат — архитектура: плагинная система, движок графов, контракт и его валидация, интеграции через MCP, клиент-серверное приложение. ИИ — содержимое отдельных блоков.

## Цель и задачи ВКР

**Цель:** разработать расширяемую платформу для построения персонализированных учебных пайплайнов на основе ИИ-агентов.

**Задачи:**

1. Проанализировать предметную область: ИИ-тьюторы, конструкторы агентов (n8n, Dify, Flowise), плагинные системы, протокол MCP.
2. Описать сценарии использования платформы в школе и вузе и декомпозировать их на шаги.
3. Выделить из шагов абстракции и на их основе определить набор блоков.
4. Спроектировать архитектуру: ядро, контракт блока, движок графа, слой LLM-провайдеров, подключение через MCP и HTTP.
5. Реализовать ядро, визуальный редактор, кабинеты преподавателя и ученика и блоки для четырёх сценариев.
6. Оценить платформу: расширяемость, качество работы блоков, пригодность на реальных учениках (мини-пилот).
7. Оценить экономический эффект внедрения.

## Сценарии использования

Четыре сценария охватывают работу преподавателя целиком: обучение ученика, проверку, подготовку материалов и обратную связь. Каждый разбит на шаги — из них в следующем разделе выводятся блоки.

### 1. Тренировка с ИИ-тьютором (школа, ЕГЭ)

Запуск: ученик открывает назначенный урок.

1. Взять задачу нужной темы и сложности из банка задач.
2. Показать задачу ученику и получить ответ: число, формулу, фото решения или код.
3. Если прислано фото — распознать решение в LaTeX, ученик подтверждает распознанное.
4. Проверить ответ по эталону: символьно (SymPy) или тестами для кода.
5. Если неверно — подсказка тьютора уровня 1–3; контролёр проверяет, что ответ не раскрыт; ученик пробует снова.
6. Три неудачи — задача проще; верно — следующая задача.
7. В конце — отчёт преподавателю в кабинет, ученику — итог в Telegram.

### 2. Проверка работ (вуз: лабораторные; школа: домашние задания)

Запуск: событие «студент сдал работу в Moodle» или расписание после дедлайна.

1. Получить список сданных работ и файлы из Moodle.
2. Извлечь содержимое: текст из PDF или DOCX, код, фото в текст.
3. Проверить: код — тестами в песочнице, текст — ИИ по критериям (рубрике) преподавателя.
4. Сформировать оценку и комментарий для каждого студента.
5. Преподаватель просматривает, правит и подтверждает.
6. Выставить оценку и комментарий в Moodle, отправить студенту письмо.

### 3. Подготовка материалов

Запуск: преподаватель вручную.

1. Получить текст лекции из файла или облака.
2. Сделать конспект и список ключевых понятий.
3. Сгенерировать вопросы и варианты заданий с эталонными решениями.
4. Проверить корректность: независимое решение, символьная проверка.
5. Преподаватель подтверждает или правит.
6. Сохранить задачи в банк платформы, выгрузить файл (PDF или DOCX) или тест в Moodle.

### 4. Аналитика и рассылки

Запуск: расписание, например раз в неделю.

1. Собрать результаты группы из хранилища платформы и оценки из Moodle.
2. Найти отстающих, типичные ошибки и темы для повторения.
3. Сформировать сводку для преподавателя.
4. Сформировать персональные сообщения ученикам или родителям с рекомендациями.
5. Преподаватель подтверждает рассылку.
6. Разослать по email или в Telegram, сводку — в кабинет преподавателя.

## От сценариев к блокам

25 шагов четырёх сценариев сводятся к восьми абстракциям и служебным узлам логики. Это и есть обоснование набора блоков для записки. Номер «2.3» означает сценарий 2, шаг 3.

| Абстракция | Шаги из сценариев | Чем отличаются шаги (= настройка блока) |
| --- | --- | --- |
| **Триггер** | запуски всех четырёх сценариев | ученик открыл урок · событие в Moodle · расписание · вручную |
| **Источник данных** | 1.1, 2.1, 3.1, 4.1 | банк задач и хранилище платформы · Moodle · файл · облако |
| **Преобразование** | 1.3, 2.2 | фото → LaTeX · PDF или DOCX → текст · извлечение кода |
| **Взаимодействие с учеником** | 1.2, 1.5 | показать задачу и получить ответ · диалог с тьютором |
| **Проверка** | 1.4, 2.3, 3.4 | по эталону (SymPy) · тесты в песочнице · по рубрике с помощью ИИ |
| **ИИ-обработка** | 2.4, 3.2, 3.3, 4.2, 4.3, 4.4 | промпт-шаблон и формат результата: комментарий, конспект, задания, сводка, письмо |
| **Подтверждение преподавателем** | 2.5, 3.5, 4.5 | что показать и что можно править |
| **Получатель** | 1.7, 2.6, 3.6, 4.6 | кабинет · Telegram · email · Moodle · файл · банк задач |

**Служебные узлы логики** (не блоки, а часть движка): условие (1.5, 1.6), цикл с ограничителем (1.5), «для каждого» — выполнить ветку для каждого элемента списка (2.3–2.6, 4.4–4.6).

**Что из этого следует для архитектуры:**

- Источник и Получатель — одна и та же идея с разными направлениями: **адаптер к внешней системе**. Адаптеры удобно делать MCP-серверами — их же смогут вызывать агенты.
- Проверка и ИИ-обработка часто идут в паре: ИИ генерирует, проверка контролирует. Это та же схема, что у тьютора с контролёром.
- Подтверждение — универсальная «точка паузы» перед любым действием с последствиями.

## Каталог блоков

Восемь блоков; у каждого несколько реализаций (адаптеров), которые выбираются в настройках. Жирным — минимум, без которого не работает ни один сценарий.

| Блок | Реализации в ВКР | Вход → выход | Как подключается |
| --- | --- | --- | --- |
| **Триггер** | **вручную**, **ученик открыл урок**, расписание (cron), событие Moodle | — → `Event` | встроенный |
| **Источник данных** | **хранилище платформы** (банк задач, группы, результаты), **файл**, Moodle, облако (Яндекс Диск) | `Query` → `Data` | хранилище и файл — встроенные; Moodle и облако — MCP |
| **Преобразование** | **документ → текст** (PDF, DOCX), фото → LaTeX | `File` → `Text` / `Answer` | встроенный; распознавание — через LLM |
| **Взаимодействие с учеником** | **показать задачу и принять ответ**, **ИИ-тьютор** с подсказками 1–3 и контролёром | `Task` → `Answer` / `Hint` | встроенный, ждёт ученика |
| **Проверка** | **по эталону (SymPy)**, тесты кода в песочнице, по рубрике с помощью ИИ | `Answer` + `Task` → `Verdict` | эталон и рубрика — встроенные; песочница — HTTP |
| **ИИ-обработка** | **шаблон промпта + схема результата**: комментарий, конспект, задания, сводка, письмо | `Data` → `Data` | встроенный, агент может вызывать MCP-инструменты |
| **Подтверждение** | **просмотр и правка преподавателем** | `Data` → `Data` | встроенный, ждёт преподавателя |
| **Получатель** | **кабинет**, **хранилище платформы**, файл, email, Telegram, Moodle | `Data` → — | кабинет и хранилище — встроенные; email, Telegram, Moodle — MCP |

**Исходы для ветвления:** Проверка — `correct` / `wrong`; тьютор — `hint` / `give_up`; Подтверждение — `approved` / `rejected`; Преобразование — `ok` / `unreadable`.

**Уровни подсказок тьютора:** 1 — наводящий вопрос; 2 — указание на метод; 3 — первый шаг. Ответ и последний шаг не выдаются никогда.

**Эталонные решения** генерирует ИИ (блок ИИ-обработки в сценарии 3), но в банк они попадают только после блока Подтверждения.

Стрелка от встроенных блоков к MCP-серверам — это агентные блоки (ИИ-обработка, тьютор), которые сами вызывают те же адаптеры как инструменты. Telegram и email здесь не отдельные клиенты, а Получатели: платформа пишет туда через MCP-адаптер.

**Путь одного шага:** триггер создаёт запуск → движок берёт текущий узел → реестр находит блок и способ вызова → блок возвращает выходы и исход → движок выбирает следующий узел → состояние сохраняется в PostgreSQL, кабинеты получают обновление по WebSocket.

## Контракт блока, MCP и HTTP

Контракт — главный инженерный результат: всё, что ядро и редактор знают о блоке, берётся из его манифеста; способ запуска блока для ядра не важен.

**Манифест (`block.yaml`):**

- `id`, `version`, `name`, `description`, `author`;
- `inputs` / `outputs` — именованные порты с типами (JSON Schema): `Event`, `Query`, `Data`, `File`, `Text`, `Task`, `Answer`, `Verdict`, `Hint`;
- `config` — настройки, из них редактор строит форму (например, у Источника: тип адаптера, курс Moodle, путь в облаке);
- `kind` — `auto` (выполняется сразу), `interactive` (ждёт ученика), `approval` (ждёт преподавателя);
- `outcomes` — исходы для ветвления;
- `runtime` — `python` (встроенный), `mcp` (MCP-сервер и имя инструмента) или `http` (URL сервиса);
- `tools` — для агентных блоков: какие MCP-инструменты агенту разрешено вызывать;
- `side_effects` — меняет ли блок что-то во внешнем мире (отправка, оценка); редактор предупреждает, если перед таким блоком нет Подтверждения.

**Интерфейс исполнения** одинаков для всех трёх runtime:

```
run(inputs, config, context) -> { outputs, outcome, events }
```

**Где MCP, а где HTTP.** MCP используется в двух ролях, и один и тот же сервер обслуживает обе:

1. **Адаптер блока.** Источник «Moodle» — это вызов инструмента `get_submissions` MCP-сервера Moodle; Получатель «email» — вызов `send_email`. Ядро вызывает инструмент детерминированно, как обычную функцию.
2. **Инструменты агента.** Блок ИИ-обработки может получить доступ к тем же серверам и сам решить, что вызвать: например, при составлении сводки заглянуть в журнал Moodle.

HTTP остаётся для простых сервисов без агентного смысла: песочница для запуска кода (`GET /manifest`, `POST /run`). Окончательное разделение уточним после реализации первых адаптеров, как и предлагал научрук.

**Сторонний разработчик** добавляет блок одним из трёх способов: Python-пакет с `block.yaml`; любой MCP-сервер плюс манифест-обёртка; HTTP-сервис по контракту.

## Исполнение: триггеры, граф и агенты

Модель гибридная: структуру урока задаёт преподаватель графом, а свободу ИИ ограничивает рамками отдельных блоков.

**Пайплайн** — JSON-описание графа: узлы (блок + настройки) и рёбра (выход → вход, условие по исходу). Первый узел всегда Триггер.

**Запуск (run)** создаётся, когда срабатывает триггер:

| Триггер | Кто или что | Пример | Как реализован |
| --- | --- | --- | --- |
| Вручную | преподаватель нажал «Запустить» | подготовка материалов | кнопка в кабинете |
| Ученик | ученик открыл назначенный урок | тренировка | ссылка на урок |
| Расписание | cron-выражение | сводка по пятницам | планировщик в очереди задач |
| Событие | внешняя система | студент сдал работу в Moodle | периодический опрос Moodle через MCP; вебхук, если доступен |

**Как движок проходит граф:**

- `auto`-блоки выполняются подряд в фоновой очереди;
- на `interactive` и `approval` запуск ставится на паузу и ждёт человека; состояние полностью в базе;
- **условие** выбирает ребро по исходу; **цикл** — ребро назад с обязательным ограничителем числа повторов;
- **«для каждого»** запускает ветку отдельно для каждого элемента списка (каждой работы, каждого студента) и собирает результаты;
- при сохранении пайплайн проверяется: типы портов, достижимость узлов, ограничители циклов, Подтверждение перед блоками с `side_effects`.

**Где работают агенты.** Внутри блоков ИИ-обработки, тьютора и проверки по рубрике. Агент получает только разрешённые в манифесте MCP-инструменты, ограниченное число шагов и схему результата. Так ИИ остаётся «внутри коробки», которую нарисовал преподаватель, — именно этого не хватало в статьях, где поведение задавалось только промптом.

**Свой движок или готовый.** Свой небольшой исполнитель на несколько сотен строк: прозрачен, легко описывается в записке, не диктует формат хранения. LangGraph — внутри агентных блоков.

## Стек и структура репозитория

Стек — минимум разных технологий и максимум того, что хорошо знает Claude Code.

| Слой | Технологии | Зачем |
| --- | --- | --- |
| Бэкенд | Python 3.12, FastAPI, Pydantic, SQLAlchemy + Alembic | API, движок, встроенные блоки |
| Фоновые задачи и расписание | Redis + arq (очередь и cron) | долгие шаги, триггеры по расписанию и опрос событий |
| База | PostgreSQL | пайплайны, запуски, задачи, события |
| MCP | официальный Python SDK MCP (клиент в ядре, свои серверы-адаптеры) | Moodle, облако, email, Telegram |
| LLM | абстракция провайдера: YandexGPT, GigaChat, OpenAI-совместимые, Ollama | выбор модели в настройках блока |
| Агенты | LangGraph внутри блоков | тьютор с контролёром, ИИ-обработка |
| Математика | SymPy, latex2sympy2 | проверка по эталону |
| Документы | pypdf, python-docx | извлечение текста и выгрузка файлов |
| Песочница | Docker с лимитами | запуск кода учеников |
| Фронтенд | React, TypeScript, Vite, React Flow, TanStack Query, KaTeX | редактор и кабинеты |
| Каналы | aiogram 3 (Telegram), SMTP (email) | Получатели |
| Наблюдаемость | Langfuse | трассировка LLM и стоимость |
| Инфраструктура | Docker Compose, GitHub Actions, VPS в РФ | деплой и CI |
| Разработка | macOS, Homebrew, uv, pnpm, OrbStack или Docker Desktop, Claude Code | локальная среда |

Для разработки адаптера Moodle нужен тестовый Moodle: поднимаем его локально в Docker, чтобы не трогать боевой сервер вуза или школы.

## Модель данных

Всё, что происходит в запусках, пишется в журнал событий — из него строятся отчёты, сводки (сценарий 4) и данные для оценки.

| Сущность | Основные поля | Связи |
| --- | --- | --- |
| User | роль (teacher / student), имя, email, telegram\_id, внешние id (Moodle) | — |
| Group | название, источник (платформа или курс Moodle) | преподаватель, ученики |
| Task | предмет, тема, сложность, условие (Markdown + LaTeX), ответ, эталонное решение, тесты, рубрика, статус (черновик / подтверждён) | автор |
| Submission | файл или текст работы, источник (платформа, Moodle), оценка, комментарий | ученик, Task или задание Moodle |
| Connection | тип (Moodle, облако, email, Telegram), адрес MCP-сервера, зашифрованные ключи | преподаватель |
| BlockRegistry | id блока, версия, манифест, runtime | — |
| Pipeline | название, граф (JSON), версия | автор |
| Trigger | тип, параметры (cron, событие), активен ли | Pipeline |
| Assignment | кому назначен пайплайн, срок | Pipeline, User / Group |
| Run | текущие узлы, состояние портов, статус | Pipeline, Trigger, ученик (если есть) |
| Approval | что на подтверждении, решение, правки | Run, преподаватель |
| Event | тип, узел, данные, время | Run |
| LLMCall | провайдер, модель, токены, стоимость, задержка | Run, Event |

**Персональные данные:** храним минимум, база на VPS в РФ, ключи доступа к Moodle и почте — в зашифрованном виде; для пилота — согласие родителей; для анализа данные обезличиваются.

## Оценка и мини-пилот

Для бакалавриата эксперимент необязателен, поэтому основная часть — инженерная оценка, а пилот показывает внедрение.

**Инженерная оценка:**

| Что проверяем | Как |
| --- | --- |
| Покрытие сценариев | Все четыре сценария собираются в редакторе из блоков каталога, без нового кода |
| Расширяемость | Сколько времени и строк кода нужно на новый адаптер (например, второе облако) и новый блок; подключение готового чужого MCP-сервера |
| Качество проверки | 50–100 реальных работ учеников; совпадение вердикта платформы с оценкой преподавателя |
| Качество распознавания | 30–50 фото решений; доля корректно распознанных |
| Утечка ответа тьютором | Скрипт-«ученик» пытается выбить ответ; доля утечек с контролёром и без |
| Сравнение моделей | Те же тесты на 2–3 провайдерах: точность, задержка, стоимость |
| Экономия времени | Сколько минут занимает проверка работ группы вручную и с платформой |

**Мини-пилот:** 2–3 недели в частной школе и онлайн-практике; ученики проходят тренировку с тьютором, преподаватель пользуется проверкой и сводкой. Собираем: сколько задач решено, сколько подсказок взято, отзывы учеников и преподавателя. Без контрольной группы — как демонстрация внедрения и источник для акта внедрения.

## Риски и порядок урезания

Главный риск — объём: четыре сценария, четыре источника и шесть получателей за двенадцать недель с нуля. Защита одна: резать адаптеры, а не сценарии и не ядро.

| Риск | Что делаем |
| --- | --- |
| Не успеваем всё | Каждый сценарий сначала работает на минимальных адаптерах (файл, хранилище, кабинет), внешние подключаются потом |
| Moodle сложнее, чем кажется | Тестовый Moodle в Docker с первой недели работы над ним; если не успеваем — сценарий 2 на файлах, адаптер Moodle описан в записке |
| Нет доступа к Moodle вуза или школы | Демонстрация на тестовом Moodle — для ВКР этого достаточно |
| ИИ проверяет работы плохо | Подтверждение преподавателем стоит по умолчанию; это же аргумент в записке |
| Тьютор выдаёт ответ | Контролёр + эталон в промпте; доля утечек — метрика оценки |
| Дорогие или нестабильные API | Абстракция провайдера, кэш, локальная модель для разработки |
| Застреваю в технологиях | Claude Code пишет каркас, ты разбираешь и правишь; раз в неделю — сессия «объясни, что здесь происходит» |

**Порядок урезания, если не успеваем:**

1. Облако — оставить только файл.
2. Telegram — только уведомления.
3. Событийный триггер Moodle — заменить расписанием.
4. Распознавание фото — ответ формулой.
5. Moodle как Получатель — выгрузка оценок файлом.

Не режем: ядро, контракт, триггеры, Подтверждение, все четыре сценария на минимальных адаптерах, хотя бы один MCP-адаптер.
