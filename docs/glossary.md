# Словарь проекта

Все технические термины из `docs/vision.md` и `docs/roadmap.md`, объяснённые простыми словами, с примером из нашего проекта. Новый термин добавляется сюда в той же задаче, где он впервые появился.

Как искать: Cmd+F по странице. Разделы идут от рабочего места к понятиям самой платформы.

## 1. Рабочее место

| Термин | Простыми словами | Пример из проекта |
| --- | --- | --- |
| Терминал | Окно, где компьютеру пишут команды текстом вместо нажатия кнопок | Во встроенном терминале (Ctrl+`) ты выполнял `gh auth login` |
| Homebrew (`brew`) | «Магазин приложений» для терминала на Mac: одной командой ставит программу | `brew install uv` поставил нам `uv` |
| Apple Silicon (arm64) | Тип процессора в новых Mac; от него зависит, какие сборки программ подходят | Образ тестового Moodle должен поддерживать arm64 |
| Docker | Программа, которая запускает другие программы в изолированных «коробках», чтобы не ставить их на Mac | PostgreSQL и Redis будут работать в Docker |
| Контейнер | Одна запущенная «коробка» с программой и всем, что ей нужно | Контейнер с тестовым Moodle |
| Образ (image) | Заготовка, из которой создаётся контейнер, как установочный диск | `hello-world` — крошечный образ, которым мы проверили Docker |
| Docker Compose | Файл со списком «какие контейнеры запустить вместе» и команда, которая их поднимает | `docker compose up` поднимет базу, очередь и бэкенд разом (задача 01) |
| OrbStack | Приложение для Mac, внутри которого работает Docker; лёгкая замена Docker Desktop | Пока OrbStack не запущен, команда `docker` не отвечает |
| Песочница | Изолированное место, где чужой код не может ничего сломать | Код ученика запускается в контейнере с ограничением времени и памяти |
| VPS | Арендованный компьютер в дата-центре, который работает круглосуточно | На VPS в РФ живёт платформа во время пилота |
| Деплой | Выкладка программы на сервер, чтобы ею могли пользоваться другие | Задача 24: платформа открывается по адресу в интернете |
| `.env` | Файл с секретами и настройками, который лежит только на твоём компьютере | В нём будет ключ YandexGPT или GigaChat |
| `.env.example` | Образец файла `.env` без самих секретов: только названия настроек | Лежит в репозитории, чтобы было понятно, что вписать в `.env` |
| Секрет, ключ API, токен | Длинная строка-пароль, по которой сервис узнаёт программу | Токен Moodle Web Services, ключ провайдера ИИ |
| Шифрование | Превращение данных в нечитаемый вид, который открывается только ключом | Ключи преподавателя от Moodle и почты хранятся в базе зашифрованными |
| Хэш пароля | Необратимый «отпечаток» пароля: проверить пароль по нему можно, а узнать — нет | Пароль преподавателя хранится только в виде хэша |

## 2. Git и GitHub

| Термин | Простыми словами | Пример из проекта |
| --- | --- | --- |
| Git | Программа, которая запоминает все версии файлов проекта и позволяет вернуться к любой | Вся история платформы хранится в скрытой папке `.git` |
| Репозиторий | Папка проекта вместе с её историей изменений | Папка `platform` на Mac и её копия на GitHub |
| Коммит | Сохранённый снимок изменений с подписью «что сделано» | Первый коммит: описание проекта, план и `.gitignore` |
| Ветка (branch) | Отдельная линия работы, которая не мешает основной | `task/07-llm` — ветка задачи 07 |
| `main` | Основная ветка, в которой всегда лежит рабочая версия | В `main` попадает только то, что прошло проверки |
| GitHub | Сайт, где хранится копия репозитория и идёт проверка изменений | `github.com/seryozhageneva/platform` |
| `gh` (GitHub CLI) | Программа для работы с GitHub из терминала | Claude создаёт через неё репозиторий и pull request |
| `origin` | Короткое имя адреса репозитория на GitHub | `git push origin main` — отправить `main` на GitHub |
| Push | Отправка своих коммитов на GitHub | После каждой задачи изменения уходят на GitHub |
| Pull request (PR) | Заявка «прошу принять изменения из ветки в `main`», где их можно просмотреть и проверить | Одна задача — один pull request |
| `.gitignore` | Список файлов, которые Git не должен замечать | `.env`, `node_modules/`, `.venv/` |
| Публичный репозиторий | Репозиторий, который видит любой человек в интернете | Наш репозиторий публичный, поэтому данных учеников в нём нет |
| Монорепо | Один репозиторий на весь проект: и бэкенд, и фронтенд, и документы | В `platform/` лежат `backend/`, `frontend/`, `docs/` |
| Worktree | Вторая рабочая копия того же репозитория, чтобы вести две задачи одновременно | С 5-й недели: одна сессия делает редактор, другая — адаптер Moodle |
| CI | Автоматическая проверка: при каждом изменении сервер сам запускает тесты | Красный CI — изменения нельзя принимать |
| GitHub Actions | Сервис GitHub, который выполняет CI | Настраивается в задаче 01 |

## 3. Claude Code

| Термин | Простыми словами | Пример из проекта |
| --- | --- | --- |
| Claude Code | ИИ-помощник, который пишет код и выполняет команды в проекте | Весь код платформы пишет он, ты читаешь и одобряешь |
| Сессия | Один разговор с Claude Code | Одна задача — одна сессия |
| Контекст | Всё, что Claude сейчас «держит в голове»: твои сообщения и прочитанные файлы | `/context` показывает, что загружено |
| `/clear`, `/compact` | Очистить контекст; сжать длинный разговор в краткое изложение | Новая задача — новая сессия или `/clear` |
| `CLAUDE.md` | Памятка в корне проекта, которую Claude читает в начале каждой сессии | Там стек, команды тестов и правила работы |
| Режим разрешений | Насколько самостоятельно Claude действует: Plan, Manual, Accept edits, Auto | Задача начинается в Plan, реализуется в Accept edits |
| Скилл (skill) | Сохранённая инструкция, которую ты вызываешь командой | `/next-task 07` — «возьми задачу 07 и составь план» |
| Субагент | Отдельный помощник со своей узкой задачей и свежим взглядом | `reviewer` проверяет изменения перед коммитом |
| Хук (hook) | Действие, которое запускается само после определённого события | После правки файла сам запускается форматтер |
| ADR | Короткая запись архитектурного решения: в чём был вопрос, что решили, что из этого следует | `docs/adr/0002-stack.md` — почему выбран такой стек |

## 4. Качество кода и тесты

| Термин | Простыми словами | Пример из проекта |
| --- | --- | --- |
| Тест | Маленькая программа, которая проверяет, что другая программа работает правильно | «Пайплайн из трёх блоков доходит до конца» |
| «Зелёные тесты» | Все тесты прошли успешно | Задача заканчивается зелёными тестами |
| pytest | Программа, которая запускает тесты на Python | `uv run pytest` |
| Юнит-тест | Тест одной маленькой детали отдельно от остальных | Тест «манифест без поля `id` отклоняется» |
| Сквозной тест (e2e) | Тест целого сценария от начала до конца | «Ученик получил задачу, ошибся, получил подсказку» |
| Фейк, заглушка | Упрощённая подделка соседней детали, чтобы тестировать без неё | Движок тестируется на фейковых блоках |
| Фейковая LLM | Подделка ИИ-модели, которая отвечает заранее заготовленным текстом | В тестах не тратятся деньги и ответы всегда одинаковые |
| Замер на настоящей модели | Отдельный ручной прогон сценариев на реальном ИИ, чтобы узнать качество | 10 попыток «выбить ответ» у тьютора, результат в `docs/eval/` |
| Линтер | Программа, которая ищет в коде ошибки и неаккуратности, не запуская его | `ruff check` для Python, `eslint` для фронтенда |
| Форматтер | Программа, которая сама выравнивает код по единым правилам | `ruff format`, `prettier` |
| ruff | Линтер и форматтер для Python | Запускается хуком после каждой правки `.py` |
| eslint, prettier | Линтер и форматтер для фронтенда | Запускаются после правки файлов во `frontend/` |
| import-linter | Проверка «кто кого имеет право подключать» | Не даёт блоку подключить движок напрямую |
| Вертикальный срез | Тонкий кусок, проходящий через все слои, от базы до экрана | «Сценарий 1 тонко насквозь, потом утолщаем» |
| Гейт | Контрольная точка плана: дальше идём, только если она пройдена | Гейт 1 — сквозной тест сценария 1 зелёный |

## 5. Бэкенд

| Термин | Простыми словами | Пример из проекта |
| --- | --- | --- |
| Бэкенд | Часть программы, которая работает на сервере и которую пользователь не видит | Движок, блоки, база данных |
| Python | Язык программирования бэкенда | Версия 3.12, ставится через `uv` |
| `uv` | Программа, которая ставит нужную версию Python и библиотеки | `uv run pytest` запускает тесты в окружении проекта |
| Виртуальное окружение (`.venv`) | Отдельная папка с библиотеками только этого проекта | Не смешивается с системным Python 3.14 |
| Библиотека, пакет | Готовый чужой код, который подключают, чтобы не писать самим | SymPy, FastAPI |
| HTTP | Способ, которым программы в сети задают друг другу вопросы и получают ответы | Браузер запрашивает у бэкенда список уроков |
| API | Набор «вопросов», на которые программа умеет отвечать другим программам | API платформы: создать пайплайн, запустить, получить журнал |
| REST | Распространённый стиль API поверх HTTP: у каждой вещи свой адрес | `GET /pipelines/5` — получить пайплайн номер 5 |
| Эндпоинт | Один конкретный адрес API | `POST /runs` — создать запуск |
| WebSocket | Постоянное соединение, по которому сервер сам присылает новости | Кабинет преподавателя сразу видит, что ученик застрял |
| FastAPI | Библиотека Python для создания API | На ней написан весь API платформы |
| OpenAPI | Автоматическое описание API в едином формате | Из него генерируется код фронтенда для запросов |
| JSON | Текстовый формат данных из пар «название: значение» | Граф пайплайна хранится как JSON |
| YAML | Похожий формат, удобнее для чтения человеком | Манифест блока `block.yaml` |
| JSON Schema | Описание того, как должен выглядеть правильный JSON | Тип порта `Task` описан схемой |
| Pydantic | Библиотека Python, которая проверяет данные по описанию | Модели контракта в `backend/core/contracts/` |
| Валидация | Проверка, что данные соответствуют правилам | Пайплайн с несоединёнными блоками не сохраняется |
| async | Способ писать код так, чтобы программа не простаивала, пока ждёт ответа | Пока модель думает, бэкенд обслуживает других учеников |
| PostgreSQL | База данных: надёжное хранилище таблиц | Пайплайны, запуски, задачи, события |
| Таблица, связь | Таблица хранит записи одного вида; связь показывает, какая запись к какой относится | Запуск связан с пайплайном и учеником |
| SQLAlchemy | Библиотека, через которую Python работает с базой | Модели в `backend/models/` |
| Миграция, Alembic | Записанный шаг изменения структуры базы; Alembic эти шаги ведёт | «Добавить в таблицу задач столбец способа проверки» |
| Репозиторий (слой данных) | Код, который умеет доставать и сохранять записи одного вида; не путать с репозиторием Git | Репозиторий задач: «найти задачи по теме и сложности» |
| Redis | Быстрое хранилище в памяти, у нас служит очередью | В очереди лежат шаги пайплайнов, ждущие выполнения |
| Очередь задач, arq | Список дел для фоновой работы; arq — библиотека, которая его обслуживает | Проверка 30 работ идёт в фоне, кабинет не зависает |
| cron | Запись расписания вида «каждую пятницу в 18:00» | Триггер «расписание» для еженедельной сводки |
| Опрос (polling) | Регулярно спрашивать «есть что-то новое?» | Раз в несколько минут платформа спрашивает Moodle о новых работах |
| Вебхук | Обратный способ: внешняя система сама сообщает о событии | В ВКР не используем: Moodle так не умеет без плагина |
| SMTP | Стандартный способ отправки электронной почты | Получатель «email» шлёт письма через SMTP |

| Langfuse, трассировка | Журнал всех обращений к модели: что спросили, что ответила, сколько стоило | Видно, почему тьютор дал плохую подсказку |
| Распознавание фото | Превращение фотографии рукописного решения в текст и формулы | Блок «фото → LaTeX», ученик подтверждает распознанное |

## 8. Математика, документы, внешние системы

| Термин | Простыми словами | Пример из проекта |
| --- | --- | --- |
| SymPy | Библиотека Python, которая умеет алгебру: упрощать, сравнивать выражения | Понимает, что `2x + 2` и `2(x + 1)` — одно и то же |
| Символьная проверка | Сравнение ответов как математических выражений, а не как текста | `0.5` и `1/2` засчитываются одинаково |
| latex2sympy2 | Библиотека, которая переводит формулу из LaTeX в вид, понятный SymPy | Ответ ученика `\frac{1}{2}` превращается в выражение |
| Эталонное решение | Правильное решение задачи, подтверждённое преподавателем | С ним сверяется ответ; тьютор по нему строит подсказки |
| Рубрика | Список критериев, по которым оценивается работа | «Верный метод — 2 балла, верный ответ — 1 балл» |
| pypdf, python-docx | Библиотеки для чтения PDF и файлов Word | Блок «документ → текст» |
| Файл импорта вопросов Moodle | Файл особого формата, из которого Moodle сам создаёт вопросы теста | Сценарий 3: преподаватель загружает его в Moodle вручную |
| Moodle | Система дистанционного обучения, которой пользуются вузы и школы | Источник работ и получатель оценок в сценарии 2 |
| Moodle Web Services | API Moodle: способ программно получать работы и ставить оценки | Им пользуется MCP-сервер Moodle |
| Telegram-бот, aiogram | Программа-собеседник в Telegram; aiogram — библиотека для таких ботов | Бот присылает ученику итог урока |

## 9. Понятия платформы

| Термин | Простыми словами | Пример из проекта |
| --- | --- | --- |
| Пайплайн | Схема учебного процесса из блоков и стрелок: что за чем выполняется | «Тренировка»: взять задачу → показать → проверить → подсказать |
| Блок | Один кирпичик пайплайна, который делает одно дело | «Проверка по эталону» |
| Категория блока | Одна из восьми групп, на которые делятся блоки | «Источник: Moodle» и «Источник: файл» — категория «Источник» |
| Плагин | Дополнение, которое можно добавить, не меняя саму программу | Сторонний блок — плагин платформы |
| Адаптер | Блок или сервер, который соединяет платформу с внешней системой | MCP-сервер Moodle |
| Контракт блока | Договор о том, как выглядит любой блок и как ядро с ним общается | Соблюдаешь контракт — блок встаёт в платформу без переделок |
| Манифест (`block.yaml`) | Паспорт блока: название, входы, выходы, настройки | Из манифеста редактор узнаёт, как блок нарисовать |
| Порт | Вход или выход блока, к которому тянется стрелка | У «Проверки» входы «ответ» и «задача», выход «вердикт» |
| Тип порта | Какой вид данных проходит через порт | `Task`, `Answer`, `Verdict`, `Hint`, `Data`, `File`, `Text` |
| `Data` с уточнением | Общий тип «данные» с пометкой, что внутри и список ли это | «Список работ» нельзя подать туда, где ждут «конспект» |
| `config` | Настройки блока, которые преподаватель заполняет в форме | У «Источник: Moodle» — курс и задание |
| `kind` | Как блок выполняется: сразу (`auto`), ждёт ученика (`interactive`) или преподавателя (`approval`) | «Показать задачу» — `interactive` |
| Экран блока (`screen`) | Какой из готовых экранов платформы показать человеку | Форма ответа, подсказка, таблица на подтверждение |
| Исход (`outcome`) | Чем закончился блок; по нему выбирается следующая стрелка | У «Проверки»: `correct` или `wrong` |
| `runtime` | Как блок запускается: код на Python, MCP-сервер или HTTP-сервис | Песочница — `http`, «Источник: Moodle» — `mcp` |
| `tools` | Какие инструменты разрешены агенту внутри блока; только чтение | Агенту сводки разрешён `get_grades` |
| `side_effects` | Пометка, что блок что-то меняет во внешнем мире | «Отправить письмо» — да, «Проверка» — нет |
| Граф | Схема из точек и стрелок между ними | Пайплайн хранится как граф |
| Узел | Одна точка графа: блок со своими настройками | Узел «Проверка по эталону» в пайплайне «Тренировка» |
| Ребро | Стрелка между узлами: куда идут данные и при каком исходе | От «Проверки» при `wrong` — к тьютору |
| Движок | Часть ядра, которая шаг за шагом выполняет пайплайн | Берёт текущий узел, запускает блок, выбирает следующий |
| Реестр блоков | Список всех установленных блоков с их манифестами | По нему редактор показывает палитру блоков |
| Валидатор | Проверка пайплайна перед сохранением | Не даёт сохранить цикл без ограничителя |
| Триггер | То, что запускает пайплайн | Вручную, ученик открыл урок, расписание, событие Moodle |
| Запуск (run) | Одно конкретное выполнение пайплайна | Урок Пети по теме «Логарифмы» 3 ноября |
| Условие | Развилка: по какой стрелке идти в зависимости от исхода | Верно — следующая задача, неверно — подсказка |
| Цикл с ограничителем | Стрелка назад с обязательным пределом числа повторов | Не больше трёх подсказок на задачу |
| «Для каждого» | Узел, который выполняет ветку отдельно для каждого элемента списка | Проверить каждую из 30 сданных работ |
| Источник | Категория блоков, которые достают данные | Банк задач, файл, Moodle, облако |
| Преобразование | Категория блоков, которые переводят данные из одной формы в другую | PDF → текст, фото → LaTeX |
| Взаимодействие с учеником | Категория блоков, которые показывают что-то ученику и ждут ответа | «Показать задачу и принять ответ», тьютор |
| Проверка | Категория блоков, которые выносят вердикт | По эталону, тестами, по рубрике |
| ИИ-обработка | Категория блоков, где модель готовит текст по шаблону | Комментарий, конспект, задания, сводка, письмо |
| Подтверждение | Категория блоков, которые ставят запуск на паузу до решения преподавателя | Таблица оценок перед отправкой в Moodle |
| Получатель | Категория блоков, которые отдают результат наружу | Кабинет, файл, email, Telegram, Moodle |
| ИИ-тьютор | Блок, который выдаёт ученику одну подсказку нужного уровня | После неверного ответа — наводящий вопрос |
| Уровни подсказок | 1 — наводящий вопрос, 2 — указание на метод, 3 — первый шаг | Ответ и последний шаг не выдаются никогда |
| Контролёр | Второй агент, который проверяет подсказку тьютора перед показом | Если в подсказке есть ответ, она не показывается |
| Утечка ответа | Ситуация, когда тьютор раскрыл готовый ответ | Доля утечек — одна из метрик оценки |
| Предварительный вердикт | Оценка ИИ, которую преподаватель ещё не просмотрел | Развёрнутое решение в уроке: урок идёт дальше, оценку можно исправить |
| Параметры пайплайна | Значения, которые заполняются при назначении, а не зашиты в схему | Тема, стартовая сложность, число задач |
| Назначение (assignment) | Запись «этот пайплайн с такими параметрами назначен этим ученикам до такого срока» | «Тренировка, логарифмы, 8 задач» для 11-го класса |
| Личная ссылка | Ссылка, по которой ученик входит без почты и пароля | Её выдаёт преподаватель при добавлении ученика |
| Кабинет | Личная страница ученика или преподавателя | У преподавателя: запуски, журнал, очередь подтверждений |
| Банк задач | Хранилище задач с ответами, решениями и способом проверки | Из него «Источник» берёт задачу по теме и сложности |
| Журнал событий | Запись всего, что произошло в запусках | Из него строятся отчёты и данные для оценки |
| Подключение (connection) | Сохранённый доступ преподавателя к внешней системе | Адрес Moodle и зашифрованный токен |
| Ядро | Основная часть платформы, которая не зависит от конкретных блоков | Движок, контракт, реестр, валидатор |
