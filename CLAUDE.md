# CLAUDE.md

Платформа для построения персонализированных учебных пайплайнов на основе ИИ-агентов (ВКР): преподаватель в визуальном редакторе собирает учебный процесс из блоков-плагинов с единым контрактом.

## Документы

- `docs/vision.md` — что строим и почему; в конце раздел принятых решений и допущений.
- `docs/roadmap.md` — 37 задач с критериями «готово, когда».
- `docs/glossary.md` — словарь терминов.
- `docs/open-questions.md` — нерешённые вопросы; загляни сюда перед планом задачи.
- `docs/contract.md` — контракт блока и формат пайплайна; примеры — в `docs/examples/`, схемы — в `docs/schemas/`.
- `docs/adr/` — архитектурные решения.

## Стек

- Бэкенд: Python 3.12 (через `uv`), FastAPI, Pydantic, SQLAlchemy + Alembic, PostgreSQL, Redis + arq.
- Фронтенд: React, TypeScript, Vite, React Flow (через `pnpm`).
- ИИ: LangGraph внутри блоков, MCP для адаптеров к внешним системам, слой провайдеров LLM.
- Инфраструктура: Docker Compose (OrbStack), GitHub Actions.

## Структура

Папки созданы в задаче 01; наполняются по задачам карты.

```
backend/core/            движок, реестр, валидатор
backend/core/contracts/  модели контракта
backend/                 triggers/ api/ llm/ mcp_client/ models/
blocks/                  встроенные блоки, каждый — пакет с block.yaml
mcp_servers/             адаптеры: moodle, cloud, email, telegram
services/sandbox/        HTTP-блок запуска кода
frontend/                редактор и кабинеты
tests/e2e/               сквозные тесты сценариев
docs/  experiments/
```

## Команды

Все команды запускаются из корня репозитория.

```
uv sync                          установить библиотеки в .venv
docker compose up -d --wait      поднять PostgreSQL и Redis и дождаться готовности
docker compose ps                состояние сервисов
docker compose down              остановить сервисы (данные базы сохраняются)
uv run alembic upgrade head      применить миграции к базе (после правки backend/models/tables.py нужна новая миграция)
uv run pytest                    тесты; тестам базы нужен запущенный PostgreSQL, они идут на отдельной базе platform_test
uv run ruff format --check .     проверка оформления кода
uv run ruff check .              линтер
uv run lint-imports              правила импортов из .importlinter (ADR 0003, 0006)
uv run python -m backend.core.contracts.schema_export    обновить docs/schemas/ после правки контракта
uv run python -m experiments.llm_check    ручной вызов настоящей модели: идёт в сеть, нужны ключ и сертификат в .env (ADR 0012)
uv run python -m backend.api     сервер API на http://127.0.0.1:8000, описание — на странице /docs; нужны база и LLM_PROVIDER в .env (ADR 0013)
uv run python -m experiments.api_check    ручная проверка API на поднятом сервере: пишет в рабочую базу выдуманного преподавателя и его ответы на паузе
```

CI (`.github/workflows/ci.yml`) запускает то же самое на каждый pull request. Тесты и линтер фронтенда появятся в задаче 13.

## Правила

1. Одна задача — одна ветка `task/NN-название` — один pull request.
2. Контракты в `backend/core/contracts/` не меняются без отдельной задачи и ADR. Не хватает чего-то в контракте — остановись и предложи изменение.
3. Задача заканчивается зелёными тестами; показывай вывод тестов, а не «всё работает».
4. Модули связаны только через контракты: блок не импортирует движок, движок не импортирует блоки.
5. В тестах — фейковая LLM; реальные модели только в ручных прогонах и замерах. При разработке — на выдуманных данных; работы настоящих учеников обрабатываются только на сервере пилота.
6. После задачи отметь её в `docs/roadmap.md`; если принималось архитектурное решение — добавь ADR в `docs/adr/`.
7. Новые термины — в `docs/glossary.md`.
8. Автор учится и не программист: отвечай по-русски, объясняй решения простыми словами, в конце задачи — 3 пункта «что важно понимать про эту задачу на защите».
9. При сжатии контекста всегда сохраняй: номер текущей задачи, список изменённых файлов, команды тестов.
10. Репозиторий публичный. В него не попадают данные учеников, результаты пилота с именами, согласия, ключи, пароли и адреса боевых серверов. Секреты — только в `.env`; читать `.env` и просить показать ключ нельзя.
11. Фамилия, имя, отчество и контакты научного руководителя не появляются нигде в сети: ни в файлах репозитория, ни в сообщениях коммитов, ни в pull request и issue, ни в опубликованных страницах и документах. Пиши «научный руководитель» или «научрук». То же относится к другим людям, кроме автора: преподавателям, ученикам, родителям.
12. Ничего не устанавливай и не удаляй без подтверждения автора. Если что-то пошло не так — не обходи проблему, а объясни и предложи варианты.
